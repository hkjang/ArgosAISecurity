# 정책 신뢰성 및 사전 검증

서명 정책을 설정하면 에이전트는 동일한 바이트의 서명, 정책 ID·버전·시각·배포 대상·서명키 ID, 탐지·대응 설정을 검증한다. 성공한 정책 원문·설정·최대 수락 버전·감사 기록은 하나의 SQLite 트랜잭션으로 저장한다. 검증 또는 저장 실패 시 에이전트 시작을 중단하며 로컬 기본 정책으로 전환하지 않는다.

## 서명과 활성화

로컬 `argos.toml`의 정책 설정은 운영자가 관리하는 신뢰 경계다. 정책 파일이 신뢰 키나 서버 소속을 스스로 추가할 수 없다.

```toml
[policy]
path = "/etc/argos/policy.toml"
policy_id = "production"
host_id = "web-01"
groups = ["web", "production"]
# 기본: <db_path>.policy-state/state.sqlite3
# state_path = "/var/lib/argos/policy-state/state.sqlite3"

[policy.trusted_keys]
release-2026 = "<Ed25519 공개키 hex 64자>"
```

서명할 `policy.toml`은 다음 구조다. 아래 Unix 밀리초 값은 형식 예시이므로 발급·적용·만료 시각을 실제 배포 기간에 맞게 바꾼다.

```toml
version = 1
policy_id = "production"
key_id = "release-2026"
issued_at_ms = 1790330000000
not_before_ms = 1790330000000
expires_at_ms = 1790416400000
target_hosts = ["web-01"]
target_groups = ["production"]

[detection]
window_secs = 10
mass_change_threshold = 30
min_changed_files = 5
entropy_threshold = 7.2
detect_score = 40.0

[response]
auto_block = false
block_score = 80.0
```

`issued_at_ms <= not_before_ms <= 현재 시각 < expires_at_ms`이며 시작 시각은 만료보다 작아야 한다. 버전은 1~9,223,372,036,854,775,807이다. ID는 1~128자의 영문·숫자·`-_.:@`만 허용한다. 대상 호스트 또는 그룹을 하나 이상 명시한다. 두 목록이 모두 있으면 **호스트 일치와 그룹 중 하나의 일치가 모두 필요**하다. 와일드카드는 지원하지 않는다.

```bash
argos policy gen-key
# 출력한 비밀키는 관리 머신의 권한 0600 파일에 보관한다.
argos policy sign policy.toml --key-file policy.signing-key
argos --config argos.toml policy verify
argos-agent --config argos.toml
argos --config argos.toml policy status --limit 100
argos --config argos.toml policy show
```

서명은 정규화하지 않은 파일 전체를 대상으로 하므로 주석이나 공백도 바뀌면 다시 서명해야 한다. 운영 활성화는 일반 파일만 읽으며 심볼릭 링크·디렉터리·FIFO를 거부한다. 원문은 최대 1 MiB, 서명 파일은 최대 256바이트다. 한 번 읽은 원문을 검증한 뒤 그대로 파싱해 파일 교체 경쟁을 막는다.

`verify`는 읽기 전용이다. 신뢰 키 설정이 있으면 서명·대상·유효기간·설정만 검사하며, 영구 버전 검사나 정책 적용은 하지 않는다. 이전 `pubkey`만 있는 설정에서는 서명만 검사했다고 표시한다. 실제 재사용·다운그레이드 검사는 에이전트 시작 시 실행한다. `show`는 영구 저장된 수락 정책을 보여주며, 현재 후보 파일을 적용된 것으로 표시하지 않는다.

## 영속 버전과 승인된 롤백

동일 버전·동일 SHA-256 정책은 재시작 복원으로 허용하지만, 매번 키·시각·대상을 다시 확인한다. 같은 버전의 다른 바이트와 낮은 버전은 정상 서명이어도 거부한다. 로컬 설정의 정책 ID만 바꿔 기존 상태의 최대 버전을 초기화할 수도 없다. 여러 프로세스가 동시에 적용하면 `BEGIN IMMEDIATE`와 버전 키 제약으로 순서를 결정한다.

과거 설정으로 복원할 때도 **새로운 더 높은 버전**으로 서명한다. 탐지·대응 설정을 이전에 수락한 정책과 동일하게 작성하고 다음 메타데이터를 넣는다.

```toml
# 최상위 version은 현재 최대 수락 버전보다 높게 지정한다.
[rollback]
source_version = 1
source_sha256 = "<policy status에서 확인한 원본 정책 SHA-256>"
approval_id = "CHG-2026-0042"
reason = "배포 후 확인한 회귀 문제로 검토된 이전 설정 복원"
```

참조한 버전·해시는 로컬 수락 이력에 있어야 한다. 설정 불일치, 빈 승인·사유, 승인 ID 재사용을 거부한다. 사유는 제어문자 없는 최대 512바이트다. 새 정책의 대상·유효기간·서명키 검증도 그대로 적용한다. 서명권자가 승인 ID·사유를 보증하는 모델이며 외부 ITSM 승인이나 두 사람 승인을 자동 확인하지 않는다. 최대 수락 버전은 내려가지 않는다.

`policy status`는 `active`와 최근 `audit`를 JSON으로 출력한다. `accepted`, `restarted`, `rollback_accepted`, `rejected` 결과와 버전·해시·키 ID·승인 ID, 고정된 거부 코드가 남는다. 잘못된 정책 원문이나 파싱 오류의 비밀값은 감사 메시지에 넣지 않는다. 수락 원문에는 승인 사유도 보존된다. 감사 행은 최신 10,000건으로 제한하고 조회는 최대 1,000건이다. 롤백 근거인 수락 정책 이력은 자동 정리하지 않는다.

`active`는 마지막으로 수락하여 영속 저장한 설정이다. 이후 파일 센서 시작이나 보고 연결까지 성공했다는 증거는 아니므로 에이전트 생존·보호 상태와 함께 확인한다. 상태 DB와 설정을 같은 트랜잭션에 기록한 뒤 그 설정을 실행하며, 메모리와 실행 중 프로세스까지 SQLite 트랜잭션에 포함하는 것은 아니다.

## 이전 설정에서 이전하기

1. `policy.pubkey`만 사용했다면 공개키에 이름을 부여해 `[policy.trusted_keys]`로 옮긴다. 로컬 정책 ID·서버 ID·그룹을 지정한다.
2. 정책에 위 메타데이터를 추가하고 버전을 증가시켜 다시 서명한다. 이전 형식은 서명·사전 비교에 사용할 수 있지만 운영 활성화는 거부된다.
3. 검증 후 관찰 모드로 시작하고 `policy status`의 수락 버전·해시·감사 결과를 확인한다. 이미 정책 상태가 있다면 삭제해 버전을 초기화하지 않는다.
4. 키를 교체할 때는 로컬 신뢰 목록에 새 키를 추가하고 그 키로 새 버전을 서명한다. 기존 키 제거는 다음 검증·재시작부터 적용되며 자동 키 배포·폐기는 제공하지 않는다.

상태 디렉터리는 현재 에이전트 계정 소유의 전용 `0700`, 파일은 `0600`이어야 한다. 심볼릭 링크·다중 하드링크·다른 계정 소유·그룹/전체 공개 상태 파일을 거부한다. SQLite FULL 동기화, 상태 디렉터리 동기화, 수락·감사 동시 커밋을 사용한다. 상위 디렉터리와 로컬 설정도 신뢰할 수 있는 운영 계정만 변경하게 관리한다. root 또는 해당 계정이 신뢰 설정·상태 전체를 삭제하거나 과거 디스크 스냅샷으로 되돌리는 공격은 로컬 파일 권한만으로 막지 못한다.

현재 시계를 신뢰하므로 시작 전 시간 동기화가 필요하다. 실행 중에도 정책 기간을 벗어나면 해당 실행의 자동 차단을 끄고 보호 저하를 표시하며, 수락한 탐지 설정은 유지한다. 유효한 새 정책으로 재시작해야 자동 차단을 다시 활성화할 수 있다. 별도 신뢰 시계, 실행 중 정책 교체, 중앙 승인·강제 키 폐기 배포는 후속 범위다.

## 과거 이벤트로 정책 비교

```bash
argos --config argos.toml policy simulate \
  --candidate candidate-policy.toml \
  --from-ms 1760000000000 --to-ms 1760086400000 \
  --max-events 100000
```

서명 정책을 사용하는 서버의 기준은 상태 DB의 **실제로 수락한 원문과 설정**이다. 상태가 없으면 조용히 기본 정책으로 대체하지 않고 실패한다. 서명 정책을 사용하지 않으면 현재 로컬 탐지·대응 설정을 기준으로 삼는다. 후보는 서명 전에도 비교할 수 있다. DB를 읽기 전용으로 열고 실제 파일 내용 접근·정책 적용·프로세스 종료는 하지 않는다.

| JSON 항목 | 의미 |
| --- | --- |
| `coverage` | 요청·준비 구간, 저장된 전체/조회/평가 건수, 잘림, 마지막 시각, 엔트로피 누락 |
| `baseline`, `candidate` | 정책별 알림, 개별 프로세스 탐지 이벤트, 임계치 진입 횟수 |
| `aggregate_alerts` | 경로·계정·계보의 여러 시간창 집계 알림. 개별 PID 자동 차단으로 변환하지 않음 |
| `aggregation_evidence_truncated` | 집계 메모리 상한으로 일부 근거가 제외됨 |
| `threshold_targets`, `would_block_pids` | 프로세스 인스턴스별 임계치 통과·예상 자동 차단 대상 |
| `delta`, `warnings` | 정책 차이·새 대상·누락·불가능한 임계치·재생 한계 |

준비 구간은 두 정책의 기본 시간창과 활성화한 모든 집계 시간창 중 가장 긴 구간이다. 요청 구간 양 끝을 포함하고 시각·DB ID 순서로 재생한다. 저장된 당시 엔트로피와 내용 표본만 사용하므로 다른 샘플 위치·크기 수집을 재현하지 못한다. `--max-events`는 준비 구간 포함 1~1,000,000건이며 상한에 걸리면 앞부분만 재생하고 누락을 표시한다.

PID·시작 시각·부팅 ID가 없는 이벤트는 자동 차단 예상 대상에서 제외한다. 승인 작업에 필요한 맥락이 없으면 예외를 적용하지 않는다. 센서 종류는 현재 설정에서 가져오므로 과거 센서와 같아야 비교가 의미 있다. 실제 차단 후 달라질 사건 흐름이나 차단 성공은 재현하지 않는다. 정상 배포·백업과 공격 시험을 비교하고 관찰 모드·소수 서버 적용을 거쳐 운영 범위를 넓힌다.

## 검증

```bash
cargo test -p argos-policy
python3 scripts/security-scenarios.py --bin-dir /path/to/binaries
```

단위 검증에는 서명 변조·키 ID·만료·미도래·대상 불일치, 재시작 후 재사용/다운그레이드, 동시 적용, 승인 롤백, 감사 저장 실패의 원자적 취소, 비밀값 비노출, 전용 상태 권한, 파일 종류 제한이 포함된다. 정책 재생은 긴 준비 구간과 집계 알림을 검증하고 집계만으로 종료 대상을 만들지 않는다. 실제 운영 성능·탐지율·전원 차단 내구성은 별도 환경 시험이 필요하다.
