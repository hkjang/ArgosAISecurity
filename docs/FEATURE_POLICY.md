# Argos 정책 서명 및 사전 검증

## 과거 이벤트로 정책 비교

`argos policy simulate`는 저장된 이벤트에 기존 정책과 후보 정책을 재적용합니다. DB는 읽기 전용으로 열며 실제 정책 적용, 감시 파일 내용 접근, 프로세스 종료를 하지 않습니다. 후보 정책은 서명 전에 비교할 수 있고, 운영 적용에는 기존 서명 검증이 계속 필요합니다.

```bash
argos --config argos.toml policy simulate \
  --candidate candidate-policy.toml \
  --from-ms 1760000000000 --to-ms 1760086400000 \
  --max-events 100000
```

기존 정책은 현재 설정과 검증된 정책 파일을 합쳐 구성하고, 센서 종류는 현재 설정에서 가져옵니다. 과거 수집 당시 센서와 같아야 의미 있는 비교가 됩니다. 후보 파일은 `version`, `[detection]`, `[response]`를 갖는 일반 정책 TOML입니다. 모든 비교 값은 JSON으로 출력됩니다.

| JSON 항목 | 의미 |
| --- | --- |
| `coverage` | 요청 구간, 준비 구간, 저장된 전체 건수, 재생 건수, 잘림 여부, 마지막 재생 시각, 엔트로피 누락 |
| `baseline`, `candidate` | 각 정책 전체 설정, 알림 수, 탐지 조건을 만족한 이벤트 수, 차단 임계치 진입 횟수 |
| `threshold_targets` | 자동 차단 비활성 상태에서도 보이는 임계치 통과 대상과 프로세스 시작 시각·부팅 ID, 최대 점수, 근거 이벤트 ID·경로 |
| `would_block_pids` | `auto_block=true`이며 프로세스 신원이 기록된 예상 자동 차단 대상의 PID 요약 |
| `delta` | 알림·탐지 증감, 새로 포함·제외된 PID 요약과 프로세스 인스턴스별 자동 차단 대상 |
| `warnings` | 조회 제한, 누락된 엔트로피, 불가능한 임계치, 재생 범위의 한계 |

재생은 두 정책 중 긴 탐지 윈도우만큼 앞선 이벤트로 준비한 뒤, 요청 구간만 집계합니다. 구간 양 끝을 포함하고 이벤트 시각·DB ID 순으로 처리합니다. 알림의 중복 억제와 차단 가능 여부는 별도로 평가하므로 억제된 알림 뒤 차단 점수가 높아지는 경우도 확인할 수 있습니다. PID 0은 차단 대상에서 제외하고 `unattributed_threshold_events`로 별도 집계합니다.

`--max-events`는 준비 구간까지 포함하며 1~1,000,000건입니다. 상한 때문에 잘리면 앞부분만 재생하고 `coverage.truncated=true`와 경고를 출력합니다. DB가 보유한 데이터의 전체 건수이며 센서가 누락 없이 수집했다는 의미는 아닙니다. 수정 시점의 저장된 엔트로피를 사용하고 현재 파일을 읽어 과거 값을 추정하지 않습니다. 샘플 크기를 0으로 설정하면 재생에서도 엔트로피를 비활성화합니다. 다른 샘플 크기 변경은 당시 파일이 없어 재현할 수 없습니다.

새 이벤트는 프로세스 시작 시각·부팅 ID를 저장하며 재생에서도 서로 다른 인스턴스를 구분합니다. 해당 정보가 없는 이전 이벤트는 임계치 통과 대상으로만 표시하고 자동 차단 예상 대상에서 제외합니다. 승인 작업 정책도 프로세스 맥락이 없는 이벤트에는 적용하지 않습니다. 센서 종류는 아직 별도로 지정해야 합니다. 더 오래된 알림 쿨다운은 완전히 복원할 수 없고, 실제 차단 후 이벤트가 달라지는 효과와 차단 성공 여부도 시뮬레이션하지 않습니다. 결과는 정책 차이 검토용이며 실제 차단·복구 검증을 대신하지 않습니다.

운영 확대는 다음 순서로 진행합니다.

1. 정상 배포·백업과 공격 시험이 포함된 구간을 비교하고 새로 차단되는 대상을 검토합니다.
2. 후보 정책의 `auto_block=false`로 관찰하고 실제 오탐과 센서 누락을 확인합니다.
3. 서명된 정책을 소수 서버에 적용해 대응 성공과 업무 영향을 확인한 뒤 확대합니다. 현재 CLI는 서버 그룹별 자동 배포를 수행하지 않습니다.

자동 검증에는 쿨다운 중 임계치 통과, 서로 다른 윈도우의 준비 구간, 후보 제외 경로, 엔트로피 비활성화, PID 0, 데이터 잘림·빈 구간, 읽기 전용 조회와 결정적 재생 테스트가 포함됩니다.

```bash
cargo test -p argos-policy -p argos-storage
```

## 서명 구현

`load_verified`는 한 번 읽은 바이트를 검증한 뒤 같은 바이트를 파싱합니다. 검증 후 파일을 다시 읽어 다른 내용을 적용하는 경쟁 조건을 피합니다.

**Argos 정책 무결성 통제 모듈**은 외부 침입자가 서버 에이전트의 차단/탐지 파라미터 설정을 임의 개조하여 탐지를 회피하려는 위협 시도를 차단하기 위해, 암호학적인 Ed25519 공개키 기반 서명 검증을 거친 화이트리스트 구성 정보만 인가하는 무결성 보호 솔루션입니다.

## 1. 핵심 설계 및 컴포넌트

정책 서명 검증은 [argos-policy](file:///d:/project/ArgosAISecurity/crates/argos-policy/src) 라이브러리가 전담합니다.
- **`Policy`** ([lib.rs](file:///d:/project/ArgosAISecurity/crates/argos-policy/src/lib.rs)): 외부 배포용 정책 데이터 형식으로 버전 값(`version`), 탐지 필터 구성(`DetectionConfig`), 대응 제어 파라미터(`ResponseConfig`)가 집약된 구조체입니다.
- **`ed25519_dalek`**: Ed25519 타원곡선 암호 디지털 서명(Edwards-curve Digital Signature Algorithm) 표준 규격을 지원하는 암호 라이브러리 엔진입니다.

## 2. Ed25519 기반 서명 및 정책 무결성 검증 원리

Argos는 정책 작성 시 설정 바이트 전체에 관리자 서명키를 서명해 안전한 무변조 증명을 확증합니다.

```
[관리 콘솔 측 작업]                     [대상 노드 서버 에이전트 측 검증]
정책 구성 (policy.toml) 작성             서명된 파일과 .sig 서명 해시 파일 로드
        │                                             │
        ▼                                             ▼
비밀 서명키(SigningKey) 로드                 설정에 심어진 공개키(VerifyingKey) 로드
        │                                             │
        ▼                                             ▼
정책 원본 파일 바이트 서명                    VerifyingKey::verify(바이트, 서명) 검사
        │                                             │
        ▼                                             ├─► 성공 ➔ load_verified 완료 및 세팅 교체
policy.toml.sig 서명 파일 생성                └─► 실패 ➔ InvalidSignature 거부 및 시동 시 세팅 고수
```

### 2.1. 서명 대상 정규화 회피 설계
- 구성 파일을 파싱하여 정렬화하는 가공 과정을 거치면 줄바꿈이나 공백 등 서식 차이로 인해 미세한 바이트 델타가 유발되어 올바른 서명 검증에 빈번히 실패하게 됩니다.
- Argos는 이러한 불안 요소를 원천 제거하고자 정책 설정 파일의 **원물 바이트 배열 전체를 정규화 과정 없이 100% 그대로 서명 및 대조**하는 단순하면서도 강력한 검증 설계를 적용했습니다.
- 단 1바이트의 공백 삽입이나 변조가 일어나도 암호 대조 단계(`verify_bytes`)에서 예외 없이 서명 대조 실패 에러(`PolicyError::InvalidSignature`)를 던지며 검증을 완벽히 방어합니다.

## 3. 에이전트 데몬 설정 연동 제어 로직

에이전트 데몬 서비스(`argos-agent`)가 기동될 때의 정책 유무 판독 및 교체 처리 과정은 다음과 같습니다:

1. **설정 확인**:
   - 로컬 구동용 설정 파일 `argos.toml` 내에 정책 경로(`policy.path`)와 신뢰 공개키(`policy.pubkey`) 항목이 명시되어 작동하고 있는지 헬스체크합니다.
2. **정책 파일 검증 로드 (`load_verified`)**:
   - `load_verified`는 배포 정책 파일(예: `policy.toml`) 및 서명 해시가 기입된 파일(예: `policy.toml.sig`)을 쌍으로 로드합니다.
   - hex 코드로 저장된 64자(32바이트) 검증용 공개키 문자열을 암호 검증키 개체(`VerifyingKey`)로 변환합니다.
   - `.sig`에 기록된 128자(64바이트)의 서명 hex 코드를 디코딩하여 서명 바이트(`Signature`)로 바꿉니다.
   - 공개키를 투입해 파일의 무결성 서명 확인 작업을 기동합니다.
3. **폴백 및 격리 처리**:
   - 만약 침입자가 임의로 정책 데이터 파일의 차단 및 탐지 옵션을 강제 해제하거나 백업 예외 디렉터리를 자신들의 거점으로 조작해 놓은 상태라면, 서명 불일치로 인해 검증이 차단됩니다.
   - 검증 에러 발생 시, 에이전트는 기형 정책의 메모리 적용을 즉각적으로 거절(Abort)하고 시동 시 가지고 있던 안전 지대의 자체 기본 설정을 강제로 고수(Fallback)하여 취약점이 유발되지 않도록 완벽히 제어합니다.
