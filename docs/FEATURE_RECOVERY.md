# 안전한 복구 지점

`argos-recovery`는 **객체 무결성**, **정상본 판정**, **사고 증거 보존**을 별도로 관리한다.
SHA-256 검증 성공은 저장된 바이트가 바뀌지 않았다는 뜻이며, 그 바이트가
공격 이전의 정상 내용이라는 뜻은 아니다.

## 백업과 정상본 지정

- 시작 시 베이스라인과 이후 변경 백업 모두 `known_good=false`로 저장한다.
- `BackupStore::versions(path)`가 버전 ID, 시각, 해시와 `known_good`, `trust_note`를 반환한다.
- 운영자는 별도 경로 미리보기와 배포 산출물 등 근거로 내용을 확인한 다음
  `mark_known_good(path, version_id, note)`로 정상본을 명시적으로 지정한다.
  비어 있는 판정 근거는 거부하고, 지정 전에 객체 해시도 다시 확인한다.
- 후속 조사로 정상 판정이 잘못되었음을 알게 되면
  `revoke_known_good(path, version_id, note)`로 취소한다.

정상 판정은 사람 또는 신뢰할 수 있는 외부 검증 결과를 입력하는 작업이다.
백업 성공·해시 일치·공격 탐지 이전이라는 이유만으로 자동 부여하지 않는다.

## 추천·미리보기·복구

`recommend(path, before_ms)`는 정상 판정된 버전 중 가장 최근 것을 반환한다.
공격 의심 시각을 전달하면 `timestamp_ms < before_ms`인 버전만 후보로 삼는다.
시각이 같은 경우에는 마지막으로 기록된 버전을 우선한다. 추천은 데이터를 쓰지 않는다.

`preview(path, version_id, destination)`는 선택한 버전을 해시 검증한 뒤 별도 파일로
복원한다. 미검토 버전도 검토할 수 있다. 대상 부모 디렉터리는 미리 존재해야 하며,
기존 파일·심볼릭 링크·원본 경로·백업 저장소 내부 경로로는 미리보기를 쓰지 않는다.
Unix에서는 미리보기 파일을 소유자만 읽고 쓸 수 있는 권한으로 생성한다.

`restore(path, before_ms)`는 추천 규칙으로 선택한 **정상본만** 원래 경로에 복구한다.
시점을 생략해도 미검토 최신 백업으로 대체하지 않는다. 정상본이 없거나 해시 검증에
실패하면 원본을 건드리지 않고 오류를 반환한다. 별도 임시 파일을 독점 생성하여
쓰기와 동기화를 마친 후 원본 경로로 이름을 바꾼다. Linux에서는 기존 일반 파일의
UID·GID를 임시 파일에 먼저 적용한 뒤 기본 권한 비트를 설정한다. 소유권을 보존할 권한이 없으면 원본 교체를 거부한다. setuid·setgid 등 특수
권한 비트는 항상 제거하고, 없는 경로는 0600으로 생성한다. 심볼릭 링크와 비일반
파일을 대상으로 하는 복구는 거부한다. ACL·확장 속성을 보존하는 파일시스템 스냅샷
기능은 아니다. 대상 부모 디렉터리 접근은 경로 기반이므로 공격자가 상위 디렉터리를
동시에 교체할 수 없는 관리된 경로에서 수행해야 한다.

## 사건별 보존 고정과 해제

사건 보존 참조는 `known_good`와 독립적이다. 정상본 판정을 취소해도 활성 사건 참조가
있으면 버전과 객체를 정리하지 않는다. 미검토 버전도 증거로 고정할 수 있지만, 고정만으로
정상본 복구가 허용되지는 않는다. 동일 버전을 여러 사건에 연결할 수 있으며 각 참조는
독립적으로 해제한다. 마지막 참조가 해제되어도 정상본 판정이 남아 있으면 계속 보존된다.

| API | 동작 |
| --- | --- |
| `pin_version(path, version_id, incident_id, actor, reason)` | 존재하는 경로·버전 쌍을 고정한다. 같은 활성 사건·버전 요청은 원래 참조를 반환하며 최초 근거를 덮어쓰지 않는다. |
| `pin_known_good_before(path, before_ms, incident_id, actor, reason)` | 해당 **정확한 경로**의 정상본 중 `timestamp_ms < before_ms`인 모든 버전을 원자적으로 고정한다. 해당 정상본이 없으면 오류로 보고한다. |
| `retention_pins(incident_id, include_released)` | 활성 또는 해제된 보존 참조를 조회한다. `None`은 모든 사건이다. |
| `retention_audit(incident_id)` | 버전이 정리된 뒤에도 남는 경로·해시·사건·요청자·사유·시각 및 승인 이력을 조회한다. |
| `release_pin(pin_id, approval)` / `release_incident(incident_id, approval)` | 특정 참조 또는 사건의 모든 활성 참조를 승인과 함께 해제한다. |

에이전트는 점수가 0보다 큰 탐지와 보존 요청을 이벤트 DB의 같은 트랜잭션에 저장한다.
별도 보존 작업자가 `detection-<탐지 ID>` 사건과 `argos-agent` 요청자로, 탐지 경로의
탐지 시각 이전 정상본을 고정한다. 백업 DB 잠금 대기는 이벤트 처리 스레드에 영향을
주지 않는다. 재시작과 부분 성공에도 사건·버전 고유 참조로 중복 없이 재시도한다.

백업이 활성화되어 있으면 자동 차단을 끈 관찰 모드에서도 동작한다. 점수 0인 분석 누락 알림에는 적용하지
않으며, 사건 경로 밖의 백업이나 기존 미검토 버전을 자동 정상 판정하지 않는다.
정상본이 없으면 요청을 실패로 기록하고 1초부터 최대 60초 간격으로 재시도한다. 보존 요청은 최대 10,000건이며
초과 시 탐지는 유지하고 누락을 영속 계수한다. `pin_pending`, `pin_failed`,
`pin_overflow`, `pin_completed`, `pin_worker_errors`를 `argos status`의 `backup` 객체에서 확인한다. `pin_failed`는 누적 실패 시도이며 현재 미완료 건수는 `pin_pending`이다. 보존 성공은
복구 범위 전체 확보나 원격 저장소의 삭제 방지를 의미하지 않는다.

기존 정상본은 보존 요청 처리 전에도 prune에서 유지된다. 단, 요청이 완료되기 전에
정상 판정을 수동 취소하면 사건 고정을 보장할 수 없으므로 완료된 참조를 확인한다.

CLI 예시 (`--config`는 다른 명령과 동일하게 앞에 지정한다). 버전 ID는
`restore PATH --list`에서 확인하며, 아래 `23`과 사건 ID는 예시다. `retention`은
백업 수집을 끈 상태에서도 설정된 저장소의 기존 보존을 관리할 수 있다:

```bash
argos retention pin /srv/data/report.txt --version 23 --incident INC-42 \
  --actor operator --reason "사건 관련 원본 증거 보존"
argos retention list --incident INC-42
argos retention release --incident INC-42 --approval CHG-82 \
  --approver reviewer --reason "독립 복구 검증과 사건 종료 확인"
argos retention audit --incident INC-42
argos retention list --include-released
```

`ReleaseApproval`에는 비어 있지 않은 `approval_id`, `approver`, `reason`이 필요하다.
승인자는 해제할 모든 참조의 최초 요청자와 달라야 하며, 승인 ID는 한 번의 해제
호출에만 사용할 수 있다. 사건 일괄 해제에서 한 참조라도 조건을 위반하면 전체를
거부한다. 사건·승인 ID는 ASCII 영문·숫자·`-`·`_`·`:`로 된 1~128자이며 경로를
ID로 사용하지 않는다. 요청자·사유에 빈 문자열이나 제어 문자를 허용하지 않는다.

이 승인자 문자열은 **로컬 운영자가 입력한 승인 이력**이다. CLI 실행자와 저장소
파일에 대한 OS 권한이 접근 통제 경계이며, 외부 사용자 인증·ITSM 승인 확인·원격
RBAC·실제 두 사람의 신원 확인을 제공하지 않는다. 정상 API의 이력 수정·삭제는
SQLite 트리거로 거부하지만, 저장소 파일을 삭제하거나 스키마를 수정할 수 있는
관리자/root와 전체 디스크 롤백까지 막는 불변 저장소는 아니다. 해당 위협에 대한
별도 저장소·접근 통제·외부 감사 보관은 운영 구성이 필요하다.

## 보존과 기존 DB 이전

기존 `index.db`에 없는 `known_good`·`trust_note` 열과 사건 보존·승인·감사 테이블을 트랜잭션으로 추가한다.
기존 버전·객체와 `v0.1.0`에서 지정한 정상본 판정·근거는 그대로 보존하므로 업그레이드 때문에 다시 지정할 필요는 없다.
정상본 판정이 없던 구형 DB의 버전은 미검토로 이전하며, 이 경우 기본 복구 전에 내용을 검토하고 정상본을 지정해야 한다.

`prune(keep)`는 경로별 최신 미검토 버전 `keep`개와 **모든 정상 복구 지점 및 활성 사건 고정 버전**을 보존한다.
`keep=0`에서도 정상본·사건 고정은 남는다. 정리 대상이 되려면 정상 판정이 취소되고
모든 사고 참조가 승인 해제되어야 한다. 고정과 정리는 SQLite `IMMEDIATE` 트랜잭션으로
직렬화하여, 정리가 먼저 끝났다면 고정은 없는 버전 오류를 반환하고 고정이 먼저
끝났다면 정리는 그 버전을 보존한다. 이력은 버전 삭제 후에도 보존한다.
실제 보존 수와 감사 이력은 `keep`을 초과할 수 있으므로 정상본·사건 참조 수와
저장소 용량을 함께 관리해야 한다. 에이전트는 백업 성공 처리 100회마다 정리를 시도하며, CLI `prune` 명령은 없다.

## 검증

`cargo test -p argos-recovery`는 손상된 최신본 대신 지정 정상본 복구, 정상본 없는
복구 거부, 공격 의심 시점 경계, 시각 순서가 뒤바뀐 백업의 추천, 미검토 미리보기,
기존 파일 및 원본 덮어쓰기 방지, 해시 손상 시 원본 보호, 정상본 보존·판정 취소,
구형 DB 이전을 검증한다. 추가로 다중 사건 참조·재시작 유지·정상 판정 취소 후 보존·
미검토 고정의 복구 거부·승인자 분리·승인 재사용 거부·일괄 해제 원자성·감사 이력
변경 거부·동시 고정/정리 및 `prune(0)`을 검증한다.
`python3 scripts/security-scenarios.py --bin-dir <빌드 경로>`는 실제 에이전트·CLI로
탐지에 따른 자동 고정과 수동 승인 해제·복구 거부·감사 조회를 확인한다.
실제 랜섬웨어 실행이나 시스템 파일 변경 없이 임시
디렉터리와 테스트 데이터로 수행한다.

## 복구 준비도 API

`readiness()`는 관측된 경로별 백업 수·정상본 수·최신 정상본 시각·크기 제한으로
제외된 횟수·마지막 복구 시험 시각과 결과를 반환한다. 백업이 한 번도 성공하지 않은
대용량 제외 파일도 표시한다. 아직 백업을 시도하지 않은 파일은 목록에 없으므로
감시 디렉터리 전체의 완전한 백업 범위를 보장하는 수치는 아니다.

`test_restore(path, before_ms)`는 정상본을 백업 저장소의 임시 파일에 써서 동기화한 뒤
다시 읽어 해시를 검증하고 임시 파일을 삭제한다. 원본 파일을 변경하지 않고 성공·실패
결과를 `index.db`에 보존한다. 이 검사는 백업 저장소에서의 파일 복원 가능성을 확인하며,
실제 원본 디렉터리의 쓰기 권한이나 애플리케이션 단위 일관성까지 검증하지는 않는다.


CLI `recovery-status`는 이 API 결과에 현재 감시 경로의 제한된 검사를 더한다.
`untracked_paths`는 검사에서 발견한 미기록 파일이며, `scan_truncated`는 10,000개 경로
상한·접근 실패로 전체 범위를 확인하지 못했음을 뜻한다. `--html`은 새 파일에 보고서를
쓰며, `--test PATH [--before-ms N]`는 정상본 복구 시험 결과를 기록한다.
