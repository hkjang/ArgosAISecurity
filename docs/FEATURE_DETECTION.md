# Argos 탐지·승인 작업·미끼 파일

[DetectionEngine](../crates/argos-detect/src/lib.rs)은 센서별 점수, 승인 작업의 제한된 예외, 미끼 파일 신호를 평가한다. [BehaviorScorer](../crates/argos-detect/src/scorer.rs)는 이벤트에 저장된 시각으로 슬라이딩 윈도우를 계산한다. 과거 이벤트를 같은 순서로 재생하면 같은 결과를 얻으며, 파일 내용을 다시 읽지 않는다.

## 센서별 위험 점수

| 요소 | notify | fanotify |
| --- | --- | --- |
| 변경된 고유 경로 수 / mass_change_threshold | 최대 40 | 최대 40 |
| 고엔트로피 수정 경로 수 / 변경 경로 수 | 최대 35 | 최대 60 |
| 이름 변경·삭제 이벤트 / 전체 이벤트 | 최대 25 | 미지원 |

비율은 1을 넘지 않는다. 동일 파일의 반복 고엔트로피 쓰기는 엔트로피 증거에서 한 경로로 센다. 수정 이벤트만 제공하는 fanotify에서도 기본 차단 기준 80점에 도달한다. 엔트로피가 없거나 샘플링이 비활성인 경우 해당 점수를 가산하지 않는다. 압축 파일도 엔트로피가 높을 수 있어 엔트로피 자체를 공격 판정으로 취급하지 않는다.

기본 윈도우는 10초, 대량 변경 기준은 30개, 최소 변경 파일은 5개다. 위험도 경계는 Medium 40 / High 65 / Critical 85다. 기본 모드는 파일 앞부분 최대 `entropy_sample_bytes`(기본 64 KiB)의 Shannon 엔트로피를 수집한다. 아래 다중 위치 표본을 활성화하면 그 표본으로 대체한다.

`evaluate`는 점수와 대응 가능 조건을 매 이벤트 반환한다. `alert`만 윈도우당 1회 및 직전 보고보다 +15점 상승 시 재보고 규칙을 적용한다. 따라서 80점 임계치를 넘었지만 알림이 억제된 이벤트도 차단 판단에 들어간다. `detect_score`와 `block_score`는 독립적이며 `auto_block=false`가 기본이다. PID 0은 자동 차단하지 않는다.

시작 시 0 길이 윈도우, 잘못된 수치·승인 범위를 거부하고 도달 불가능한 점수나 notify의 PID 미지원 제약을 경고한다. PID의 시작 ticks 또는 boot ID가 달라지면 이전 프로세스의 윈도우를 제거한다.

## 승인된 변경 작업

승인 작업은 로컬 설정 또는 서명된 정책의 `detection.approved_changes`에 정의한다. 외부 ITSM이나 배포 도구는 승인 ID·유효 기간·범위를 이 정책에 전달할 수 있다. 특정 ITSM 제품과 직접 통신하는 커넥터는 포함하지 않는다.

```toml
[[detection.approved_changes]]
id = "CHG-2026-0042"
valid_from_ms = 1790409600000
valid_until_ms = 1790413200000
paths = ["/srv/releases"]
exe = "/usr/local/bin/deploy"
uid = 1001
adjusted_rules = ["behavior.ransomware_pattern"]
```

예제 시각은 실제 승인 기간으로 바꾼다. 이벤트 시각이 `[valid_from_ms, valid_until_ms)` 안에 있고, 경로가 지정 디렉터리 안에 있으며, 수집 시점 실행 파일과 **유효 UID**가 모두 일치해야 한다. PID와 시작 ticks, boot ID도 있어야 한다. `..` 경로와 단순 문자열 접두사가 같은 형제 디렉터리는 승인 범위에 포함하지 않는다. notify와 이전 데이터처럼 프로세스 맥락이 없으면 예외를 적용하지 않는다.

조정은 해당 이벤트만 명시된 규칙의 증거에서 제외한다. `behavior.ransomware_pattern` 승인만으로 아래 다중 시간창 규칙까지 제외하지 않는다. 이전 미승인 이벤트의 위험 점수는 지우지 않으며 미끼 파일 규칙은 조정할 수 없다. 평가 결과의 `approved_change_id`로 어떤 승인에 따라 조정했는지 확인한다. 원본 이벤트와 프로세스 맥락은 저장해 정책 재생 시 그대로 사용한다.

## 여러 시간창과 분산 변경

기존 10초 행위 규칙은 그대로 유지한다. 아래 기능은 명시적으로 켜야 추가된다.

```toml
[detection.multi_window]
enabled = true
protected_paths = ["/srv/data"]
aggregate_by_user = true
aggregate_by_ancestry = true
max_events = 10000
max_groups = 2048
max_path_bytes = 4096
windows = [
  { window_secs = 10, min_changed_files = 5, mass_change_threshold = 30, detect_score = 65.0 },
  { window_secs = 60, min_changed_files = 8, mass_change_threshold = 40, detect_score = 65.0 },
  { window_secs = 600, min_changed_files = 12, mass_change_threshold = 60, detect_score = 65.0 },
]
```

| 규칙 | 집계 범위 | 자동 대응 |
| --- | --- | --- |
| `behavior.multi_window.instance` | PID + 시작 ticks + boot ID | 해당 인스턴스 증거가 충분하고 누락이 없을 때만 대응 정책 평가 |
| `behavior.multi_window.user_path` | 유효 UID + boot ID + 보호 경로 | 알림만 |
| `behavior.multi_window.protected_path` | boot ID + 보호 경로, 미식별 센서는 별도 범위 | 알림만 |
| `behavior.multi_window.ancestor` | 확인한 부모 인스턴스 + 보호 경로 | 알림만 |

겹치는 보호 경로는 가장 구체적인 경로에 묶는다. 계보는 수집된 최대 4단계만 사용하고 PID 1은 제외한다. 확인하지 못한 부모·시작 신원을 추론하지 않는다. PID 재사용은 다른 인스턴스로 분리한다. 알림에는 규칙·시간창·범위·참여 PID와 신원을 표시하며, 집계 알림의 `pid=0`은 특정 현재 PID에 대한 차단 지시가 아니라는 뜻이다.

승인 작업으로 예를 들어 계정 집계만 조정하려면 `adjusted_rules=["behavior.multi_window.user_path"]`를 지정한다. 다른 규칙은 계속 평가한다. 집계에서 제외할 근거는 이벤트마다 적용하며 이전 미승인 증거를 지우지 않는다.

최근 이벤트·그룹 수와 경로 길이를 제한한다. 한도에 도달하면 오래된 근거를 제거하고 `evidence_truncated`를 반환한다. 영향받은 보존 시간창 동안 누락된 인스턴스 점수를 자동 대응 근거로 사용하지 않는다. 집계 알림은 누락을 표시하며 정상적인 독립 미끼 신호는 계속 평가한다. 시간 역전 이벤트는 장기 집계에 추가하지 않고 누락으로 표시한다. 과거 재생은 가장 긴 활성 시간창의 준비 구간과 당시 저장된 맥락을 사용해야 한다.

## 부분 암호화 표본 관찰

```toml
[detection.content_sampling]
enabled = true
total_bytes = 65536
max_files = 2048
history_secs = 600
min_entropy_increase = 1.0
```

`total_bytes`는 세 위치를 합친 총 읽기 예산이며 상한은 1 MiB다. 기존 앞부분 읽기에 추가로 세 번 읽지 않는다. 파일이 예산보다 작으면 전체를 한 번 읽고, 크면 앞·중간·끝에 예산을 나눈다. 내용 증거에 위치·길이·엔트로피·실제 읽은 바이트·파일 크기·관찰 시각·전체 바이트 표본 여부를 저장한다. 파일 유형은 magic 바이트에 따른 힌트로, 파일의 정상 여부나 정확한 포맷 검증 결과가 아니다.

이전 관찰은 파일 수와 기간으로 제한한다. 같은 파일 크기·표본 위치·길이끼리만 엔트로피 차이를 비교하고 비교 대상 시각과 최대 증가량을 보관한다. **이전 표본을 정상본으로 승격하거나 복구 판정에 사용하지 않는다.** ZIP/GZIP/XZ/Zstandard/Bzip2/7z/RAR, 주요 이미지·영상/PDF/실행 파일의 높은 엔트로피만으로 암호화 증거를 추가하지 않으며 비교 가능한 증가도 요구한다. 알 수 없는 형식의 첫 고엔트로피 표본은 파일 수·행위 조건과 함께 평가한다. 정상 암호화·압축 재생성과 공격을 이 관찰만으로 완전히 구분할 수 없다.

읽기 도중 크기·수정 시각이 바뀌거나 읽기에 실패하면 성공 표본으로 반환하지 않는다. Unix에서는 심볼릭 링크와 비정규 파일을 거부하며 FIFO 교체로 읽기가 멈추지 않도록 연다. `complete=false`는 파일 바이트 전체를 관측하지 않았다는 뜻이다. 중간 표본 사이의 암호화, 동일 엔트로피 변조, 수집 이후 내용 변경을 모두 포착한다고 보장하지 않는다. 정책 재생은 저장된 표본을 사용하고 파일을 다시 읽지 않는다.

표본의 관찰 시각은 센서 이벤트 시각과 별개다. 큐에서 기다린 뒤 읽은 내용에는 이후 다른 프로세스의 쓰기가 반영될 수 있다. 따라서 표본 차이는 이벤트 PID가 해당 바이트를 변경했다는 인증된 인과 증거가 아니다.

## 미끼 파일 기반 조기 탐지

```toml
[detection]
canary_paths = ["/srv/data/.argos-canary.txt"]
```

에이전트 시작 전에 등록한 정확한 경로에 미끼를 생성한다. 기존 파일은 덮어쓰지 않는다.

```bash
argos --config /etc/argos/argos.toml canary-init /srv/data/.argos-canary.txt
```

등록 경로의 Modify, Delete, Rename은 `behavior.canary_tamper` 규칙으로 최소 95점을 부여한다. 변경 파일 수가 1개이거나, 행위 규칙에 승인 작업이 적용되거나, 일반 제외 경로에 있어도 평가한다. 미끼 파일 생성·권한 메타데이터 변경은 단독 고위험 신호로 취급하지 않는다. 파일 읽기와 정상 백업 읽기는 센서의 변경 이벤트가 아니므로 미끼 변조 탐지를 만들지 않는다.

미끼 알림에도 중복 억제가 있지만 대응 조건은 매번 평가한다. 같은 PID가 재사용되면 프로세스 식별 정보가 별도 알림 범위를 만든다. fanotify가 현재 제공하지 않는 삭제·이름 변경 신호는 notify에서만 관측할 수 있다.

## 검증 시나리오와 한계

단위 테스트의 동일한 30개 고엔트로피 파일 변경 시나리오에서 기본 fanotify 정책은 알림 3건·차단 예상 이벤트 16건을 만들고, 정확히 일치하는 배포 승인을 적용하면 각각 0건이 된다. 이후 다른 실행 파일의 동일 변경은 다시 차단 기준을 넘는다. 시간·경로·계정·실행 파일·프로세스 맥락 중 하나가 다르거나 없으면 예외를 적용하지 않는 테스트도 포함한다.

차단 예상 이벤트 수는 프로세스 수나 실제 종료 횟수가 아니다. 이 측정은 저장 가능한 합성 이벤트를 통한 규칙 검증이며 실제 고객 배포의 오탐률이나 조사 시간 단축을 측정한 결과는 아니다. 커널 센서, 프로세스 수집 경합, 실제 공격·정상 배포의 전체 흐름은 별도 환경 시험이 필요하다.

추가 회귀 시험은 긴 간격의 단일 인스턴스 변경, 여러 PID의 계정·경로·계보 집계, 시간창 경계, PID 재사용, 규칙별 승인, 메모리 상한과 누락 표시, 결정적인 재생을 검증한다. 임시 8 KiB 파일에서 앞부분을 그대로 두고 중간 또는 끝 256바이트만 변경한 시험은 총 768바이트 읽기로 해당 위치의 엔트로피 증가를 확인한다. ZIP 형태의 변경 없는 고엔트로피 표본은 암호화 증거가 되지 않는다. 이는 제한된 합성 시나리오이며 운영 탐지율·오탐률의 측정값이 아니다.
