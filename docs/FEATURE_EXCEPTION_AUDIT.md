# 승인 작업 예외 사용 감사

```bash
argos --config argos.toml policy audit-exceptions \
  --from-ms 1760000000000 --to-ms 1760086400000 \
  --max-events 100000 --expiring-within-hours 24
```

저장된 파일 이벤트에 현재 기준 정책의 `approved_changes`를 다시 적용해 예외의 매칭 가능 범위와 제거 영향을 JSON으로 출력한다. 서명 정책을 사용하는 설정에서는 영구 저장된 마지막 수락 정책, 서명 정책을 사용하지 않으면 로컬 탐지·대응 설정이 기준이다. 기준 정책의 읽기·수락 상태 처리는 기존 `policy simulate`와 같다.

이 결과는 **저장 근거를 사용한 정책 재생**이다. 사건 당시 해당 정책이 실제로 실행되었거나 예외가 실제 적용되었다는 감사 원장, 실제 차단 건수가 아니다. 정책·원본 파일·프로세스를 변경하지 않고 이벤트 DB를 읽기 전용으로 연다. 만료·미사용 결과만으로 예외를 자동 삭제하거나 정책을 적용하지 않는다.

## 매칭과 범위

탐지 엔진과 같은 기간·경로·실행 파일·유효 UID·프로세스 시작 신원 조건을 사용한다. 승인 기간은 시작을 포함하고 종료를 제외한다. PID 0, 시작 ticks 0, 비어 있는 부팅 ID, 누락된 실행 파일 등으로 신원을 확인할 수 없으면 일치했다고 추정하지 않는다. 경로는 디렉터리 구성요소 단위로 비교하므로 `/srv/data` 예외가 `/srv/database`에 적용되지는 않는다.

겹치는 승인 작업은 **정책 배열의 첫 매칭**이 우선한다. 첫 작업에 지정한 규칙이 현재 비활성이어도 뒤의 작업으로 자동 전환하지 않는다. 지원 규칙을 하나씩 남겨 같은 엔진으로 재생하므로 비활성 집계·없는 부모 계보·제외 경로를 별도 예외 구현으로 추정하지 않는다. 이 내부 진단용 규칙 투영은 정책으로 적용하거나 출력하지 않는다.

다중 시간창의 기여 수는 Create·Modify·Delete·Rename만 집계한다. 기본 행위 규칙은 현재 엔진이 취급하는 이벤트 종류를 따른다. 한 이벤트가 여러 명시 규칙에 매칭되어도 예외 전체 매칭 수·대표 근거에는 한 번만 센다. 매칭 수는 감소한 위험 점수나 막지 않은 공격 수와 같지 않다. 미끼 파일 신호와 명시하지 않은 집계 규칙은 유지된다.

## 결과 필드

| JSON 필드 | 의미 |
| --- | --- |
| `basis` | `stored_event_replay_with_supplied_policy`: 현재 입력 정책의 저장 이벤트 재생임을 명시 |
| `now_ms`, `expiring_within_ms` | 만료·임박 상태의 기준 시각과 범위. 과거 매칭 이벤트 시각과 구별 |
| `exceptions[].definition` | 검사한 승인 작업 원문 설정: ID·기간·경로·실행 파일·UID·규칙 |
| `time_status` | `not_started`, `active`, `expiring`, `expired`. 감사 실행 시각 기준 |
| `usage_status` | `matched_in_loaded_range` 또는 `no_matches_in_loaded_range`. 조회된 평가 구간의 매칭 여부 |
| `replay_matched_events`, `warmup_matched_events` | 평가 구간과 준비 구간의 중복 없는 매칭 이벤트 수 |
| `first_matched_ms`, `last_matched_ms` | 조회된 평가 구간의 첫·마지막 매칭 시각 |
| `rule_matches` | 명시한 규칙별 매칭 가능 기여 수와 준비 구간 수. 한 이벤트가 여러 규칙에 집계될 수 있음 |
| `paths`, `process_samples`, `evidence_event_ids` | 평가 구간의 대표 경로·PID/시작 ticks/부팅 ID·파일 이벤트 ID |
| `*_samples_truncated` | 대표 표본 상한으로 출력에서 빠진 항목이 있는지 표시 |
| `broad_scope_reasons` | 넓은 범위를 검토하기 위한 휴리스틱 사유 |
| `missing_identity_events`, `missing_executable_events` | 평가 구간의 신원·실행 파일 미확인 이벤트 수. 두 수는 겹칠 수 있음 |
| `matching_evidence_truncated` | 규칙별 재생에서 엔진의 근거 상한·지원하지 않는 근거로 일부 평가가 불완전함 |
| `comparison` | 기준 정책과 모든 승인 예외를 제거한 후보의 기존 `SimulationReport` |
| `warnings` | 매칭 집계의 의미·누락·해석 한계. 비교 자체의 경고는 `comparison.warnings`에도 있음 |

대표 표본은 기본 20건이다. 경로는 시간·이벤트 ID 순으로 처음 등장한 경로부터 반환하며 인기순 순위가 아니다. 반환한 경로의 `matched_events`는 조회된 평가 구간 전체에서 그 경로가 매칭한 수다. 표본에서 빠진 다른 경로도 전체 `replay_matched_events`에는 포함된다. 프로세스 표본은 같은 PID라도 시작 ticks·부팅 ID가 다르면 구분한다.

넓은 범위 표시는 루트 또는 한 단계 깊이의 경로, 24시간을 초과하는 승인 기간, 16개를 초과하는 승인 경로를 기준으로 한다. 업무 필요성이나 악성 여부를 판단한 결과가 아니며 파일시스템을 읽어 경로 종류를 확인하지 않는다. 만료 상태인 예외도 과거 승인 기간의 이벤트에는 정상적으로 매칭할 수 있다.

## 예외를 제거한 재생 비교

`comparison.baseline`은 입력 기준 정책, `comparison.candidate`는 **모든 `approved_changes`만 제거한 정책**이다. 다른 탐지·대응 설정은 같다. `delta`는 후보에서 기준을 뺀 알림·탐지 이벤트 차이와 새 임계치/자동 차단 예상 대상을 보여 준다.

자동 차단이 꺼진 기준 정책에서는 제거 후보도 꺼져 있으므로 `would_block_pids`는 비어 있다. 대신 임계치 통과와 `threshold_targets`를 검토한다. 시작 신원이 없거나 여러 프로세스를 합산한 알림만 있는 경우 실제 자동 차단 대상으로 만들지 않는다. 같은 PID의 재사용은 `new_block_targets`·`removed_block_targets`의 시작 ticks와 부팅 ID로 구별한다.

이 비교는 모든 예외를 한꺼번에 제거한 효과다. 특정 예외 하나의 영향이나 예외별 기여의 합으로 해석하지 않는다. 개별 검토가 필요하면 그 예외만 변경한 후보 파일로 [정책 사전 검증](FEATURE_POLICY.md)의 `policy simulate`를 사용한다. 알림 억제·윈도우·여러 규칙의 상호작용 때문에 매칭 이벤트 수와 알림/차단 차이는 비례하지 않는다.

## 조회·자원 상한과 미사용 판정

기존 정책 재생과 같은 가장 긴 활성 시간창을 준비 구간으로 포함한다. 파일 이벤트·전체 건수를 **한 번의 읽기 스냅샷**으로 얻은 뒤 매칭 집계와 예외 제거 비교 양쪽에 재사용한다. 조회는 양 끝을 포함하며 시각·이벤트 ID 순서다.

- `max_events`: 준비 구간을 포함한 1~100,000건. 상한에 걸리면 앞부분만 읽고 `comparison.coverage.truncated`에 표시한다.
- 승인 작업: 최대 128개, ID 256바이트, 작업당 경로 128개·명시 규칙 5개, 경로/실행 파일 4096바이트.
- 대표 표본: API에서 종류별 1~100건, CLI 기본 20건. 모든 경로 문자열이나 신원을 무제한으로 결과에 모으지 않는다.
- 임박 기간: 최대 366일. 엔진의 이벤트·그룹·내용 표본 상한은 별도로 유지한다.

`no_matches_in_loaded_range`는 조회된 평가 구간에 매칭이 없었다는 뜻이다. 준비 구간에만 매칭되었거나, 평가 구간 전에 조회 상한에 도달했거나, 필요한 프로세스 맥락이 없을 수 있다. 센서가 저장하지 못한 이벤트와 배포 당시 정책도 현재 재생으로 복원할 수 없다. 이벤트가 없다는 이유로 예외가 불필요하거나 안전하다고 확정하지 않는다.

현재 파일 내용과 `/proc`를 다시 읽지 않는다. 당시 엔트로피·내용 표본만 사용하며 다른 샘플 위치/크기로 수집한 결과, 실제 차단 후 달라지는 사건 흐름·차단 성공·운영 오탐률을 예측하지 못한다. 엔진 근거 상한에 걸린 경우 규칙별 매칭 수 역시 참고값이다.

## 개발 API와 검증

`argos_policy::audit_exceptions(store, policy, options)`는 `ExceptionAuditReport`를 반환한다. `ExceptionAuditOptions`는 기존 `SimulationOptions`, `now_ms`, `expiring_within_ms`, `sample_limit`을 받는다. 기존 `simulate()` 공개 API는 유지한다. 정책 서명·활성화·버전 상태 로직은 변경하지 않는다.

```bash
CARGO_INCREMENTAL=0 CARGO_TARGET_DIR=/tmp/argos-recovery-target \
  cargo test -p argos-policy --offline --locked --lib
```

새 감사 회귀 테스트 8개는 기간 양끝·경로·계정·실행 파일·완전한 신원, 겹치는 예외의 우선순위, 규칙별 집계·없는 계보·미끼 파일 유지, PID 재사용, 준비 구간·조회 잘림, 대표 표본 상한, 만료/임박·넓은 범위, 읽기 전용 재생의 DB 불변을 확인한다. 기존 정책 신뢰·재생을 포함한 34개 테스트가 통과했다. 실제 배포 정책 사용 감사 원장이나 운영 오탐률 측정은 이 시험의 범위가 아니다.
