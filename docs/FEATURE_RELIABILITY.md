# 전송 신뢰성과 보호 상태

탐지가 없는 서버와 보고가 중단된 서버를 구분하기 위해 에이전트는 탐지 발생과 무관하게 30초마다 생존 신호를 보냅니다. 중앙 서버는 마지막 수신 후 60초까지 `online`, 60초 초과부터 `stale`, 120초 초과부터 `offline`으로 표시합니다. 센서 정상 여부와 전송 대기 건수·누적 전송 실패 횟수를 함께 확인할 수 있습니다. 연결 상태는 센서가 정상 수집한다는 증거를 대신하지 않습니다.

## 디스크 전송 대기열

중앙 보고가 활성화되면 탐지 원본과 전송 대기를 같은 SQLite 트랜잭션으로 저장합니다. 메모리 채널에는 데이터 대신 용량 1의 깨우기 신호만 보내므로 신호가 합쳐져도 탐지는 디스크에 남습니다. 전송 스레드는 시작 시 남은 대기열을 읽고 중앙 서버의 성공 응답을 받은 후에만 해당 항목을 삭제합니다.

등록·전송 실패는 1초부터 최대 60초까지 늘어나는 간격으로 재시도합니다. 요청 하나의 제한 시간은 5초입니다. 네트워크 I/O는 전용 스레드에서 수행하며 탐지·대응 처리에서 HTTP 완료를 기다리지 않습니다. 재시작과 연결 단절 동안 대기열은 보존됩니다. 대기 중인 에이전트 ID가 바뀌면 이전 ID의 데이터는 자동으로 다른 ID에 전송하지 않습니다.

각 항목의 고정된 `delivery_id`를 중앙에 전송합니다. 중앙 DB의 `(agent_id, delivery_id)` 고유 제약으로 원격 저장 뒤 응답이 사라진 경우에도 재시도가 중복 탐지를 생성하지 않습니다. 전달 ID가 없는 이전 에이전트 요청은 호환을 위해 받지만 중복 제거 대상은 아닙니다.

대기열은 성공 응답 전 데이터를 임의로 폐기하지 않습니다. 장기간 통신 단절 시 DB 용량을 감시해야 하며 디스크가 가득 차면 저장 실패가 로그로 드러납니다. 전달 보장은 로컬 트랜잭션이 성공한 데이터에 한하며 커널 센서 수집 누락이나 디스크 고장을 복구하는 기능은 아닙니다.

## 인증과 API

운영 서버는 관리자 조회 토큰과 에이전트별로 서로 다른 토큰이 필요합니다. 등록·생존 신호·탐지 수집은 해당 에이전트의 토큰으로 인증합니다. 관리자 토큰은 수집에 사용할 수 없고 에이전트 토큰으로 전체 현황을 조회할 수 없습니다. 인증 없는 `--development` 모드는 loopback 주소에서만 실행됩니다.

| API | 용도 |
| --- | --- |
| `POST /api/v1/agents/register` | 등록·재등록 |
| `POST /api/v1/agents/heartbeat` | 센서 상태, 전송 대기·실패 건수 보고 |
| `POST /api/v1/detections` | 고정 전달 ID를 포함한 탐지 수집 |
| `GET /api/v1/agents` | 연결 상태·센서 상태·마지막 보고·전송 대기 조회 |

## 저장된 근거와 대응 결과

새 파일 이벤트는 프로세스 실행 파일·계정·시작 시각·부팅 ID를 함께 보관합니다. 과거 정책 재생은 당시 맥락을 사용합니다. 이전 DB는 읽기 전용 조회 시 새 필드를 없는 값으로 반환하고, 에이전트가 쓰기 모드로 열면 스키마를 추가합니다. 알 수 없는 과거 신원을 현재 `/proc` 값으로 보충하지 않습니다.

프로세스 대응 결과는 `response_actions`에 위험 점수, 프로세스 인스턴스, 실행 조치, 결과·오류를 별도로 보관합니다. 탐지가 발생했다는 사실과 실제 대응이 성공했는지를 구분하여 `response_results` 읽기 API로 조사할 수 있습니다.

## 검증

```bash
cargo test -p argos-storage -p argos-policy -p argos-agent -p argos-central
```

테스트는 등록 실패 후 재시도, 원격 저장 후 응답 유실과 같은 전달 ID 재사용, 탐지가 없는 동안 생존 신호, 중앙 중복 제거, 에이전트 인증 분리, 센서 중단 표시, 오래된 스키마 조회·마이그레이션을 확인합니다. 네트워크 시험은 로컬 모의 서버만 사용합니다.


## 사건 보존 대기열

탐지·중앙 전송·사건 보존 요청을 같은 이벤트 DB 트랜잭션으로 기록한다. 보존 전용 스레드는 최대 16건씩 읽은 후 이벤트 DB 읽기 잠금을 해제하고 백업 DB에서 고정을 처리한다. 백업 쓰기 잠금이 다음 탐지·대응을 기다리게 하지 않는다. 실패는 1~60초 지연으로 재시도하고, 재시작 시 미완료 요청부터 이어간다. 사건/버전 고유 참조가 부분 성공·ACK 유실의 중복을 막는다.

자동 보존은 백업이 활성화되어 있고 탐지 점수가 0보다 클 때 요청한다. 보존 요청 상한은 10,000건이다. 초과 시 탐지 자체는 기록하고 누락을 영속 계수한다. 보호 상태의 `backup.pin_pending`, `pin_failed`, `pin_overflow`, `pin_completed`, `pin_worker_errors`로 대기·실패·누락·완료·작업자 오류를 구분한다. 큐 초과나 작업자 오류는 보호 상태를 저하로 표시한다. 보존 완료 전에도 기존 정상본 보존 규칙은 유지되지만, 요청이 성공하기 전에 정상 판정을 수동 취소하면 사건 고정을 보장하지 못한다.

`analysis_incomplete`는 최근 분석에서 표본 읽기 실패 또는 집계 근거 상한에 도달했음을, `semantic_unavailable`는 현재 읽지 못하는 지정 설정 파일 수를 표시한다. 센서가 살아 있는 것만으로 모든 분석이 성공했다고 표시하지 않는다.


## 운영 조회

```bash
argos --config /etc/argos/argos.toml status
argos --config /etc/argos/argos.toml recovery-status
argos --config /etc/argos/argos.toml retention list --incident detection-42
argos --config /etc/argos/argos.toml policy status --limit 100
```

`status`는 최근 로컬 상태 파일을 읽는다. 기본 DB가 `/var/lib/argos/argos.db`이면
상태 파일은 `/var/lib/argos/argos.health.json`이다. 중앙에는 전체 상세 JSON 대신
합산한 `sensor_healthy`와 전송 대기·실패 건수를 보고한다. 중앙 연결 `online`과
로컬 보존 요청 완료는 다른 상태다.

`backup.pin_failed`·`pin_overflow`·`pin_completed`는 이벤트 DB에 보존된 누적 계수이고,
`pin_pending`은 현재 대기 건수다. 완료 건수는 성공 처리한 요청 수이며 고정한 파일·
버전 수가 아니다. `pin_worker_errors`는 현재 작업자 실행 중 오류 계수다. 과거 실패
횟수가 남더라도 재시도로 완료될 수 있으므로 대기 건수·실제 보존 참조와 함께 본다.

## v0.3.0 추가 확인

경로 접근·루트 교체·하위 마운트·검사 상한은 [보호 공백 검사](FEATURE_COVERAGE.md)로 확인한다. 시험 파일의 DB 수신은 `coverage probe`로 별도 검사한다.

v0.4.0의 [원격 파일 전송 큐](FEATURE_VAULT_QUEUE.md)는 중앙 이벤트 outbox와 별개다. 명시적 CLI 등록/전송이며 에이전트의 자동 백업 업로드나 중앙 상태 보고에 아직 연결하지 않는다. 서버의 [용량 상태](FEATURE_VAULT_CAPACITY.md)는 관리자 조회 명령으로 확인한다.

v0.5.0부터 이미 등록한 자료는 [선택적 systemd 예약 전송](FEATURE_VAULT_SCHEDULER.md)으로 처리할 수 있다. v0.7.0의 [영속 번들 작업](FEATURE_BUNDLE_JOBS.md)은 구성 목록과 청크·완료 작업을 등록하고 중단 후 자동 재개한다. 큐 전송 완료·묶음 완료·현재 정상 판정·DB 시험 성공은 각각 확인하며 중앙 생존 상태 통합은 후속이다.
