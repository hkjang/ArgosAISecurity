# 번들 자동 게시와 승인 전 시험

v0.7.0은 등록한 번들의 전송·게시를 자동 재개하고, 복구 시험과 운영 승인을 분리한다. [영속 번들 작업](FEATURE_BUNDLE_JOBS.md), [복구 CLI](FEATURE_RECOVERY_BUNDLE_CLI.md), [보관 용량](FEATURE_VAULT_CAPACITY.md)의 실제 한도·오류를 함께 확인한다.

## 등록부터 승인까지

1. `vault bundle prepare`로 백업과 계획을 고정한다. `bundle enqueue`가 구성 목록과 모든 고유 청크·게시 작업을 영속 등록한 뒤 성공을 반환한다.
2. `vault queue drain` 또는 선택한 systemd timer가 청크 전송과 register/complete를 실행한다. 등록 성공 이후 stage가 없어도 진행하며, 중단된 작업은 임대 만료 후 재시도한다. `queue jobs`·`show-bundle`에서 단계와 오류를 확인한다.
3. 원격 완료 상태가 `unknown`이면 관리자 설정으로 `bundle test --preapproval`를 실행한다. 현재 `unknown`과 같은 구성 목록·완료 증명을 시험 전후에 확인한다. SQLite는 별도 namespace, PG는 기존 전용 격리 경로를 사용한다.
4. 시험 결과와 원본 근거를 검토한 담당자가 별도로 `bundle review --decision good`를 요청한다. 시험 명령은 이 승인을 생성하지 않는다.
5. 일반 `fetch`와 `test`는 현재 `good` 판정을 확인한다. 이상을 발견하면 `review --decision revoked`를 추가해 기본 복구와 승인 전 시험을 보류한다. 조사 목적으로 명시한 `fetch --evidence-only`는 완료된 증거의 검증된 바이트를 보존한다.

예약 실행이 활성화되어 있어도 입력 파일을 자동 수집하지 않는다. 수동 `publish`/직접 `upload`도 계속 지원하며 이전 방식과 혼용한 재시도는 같은 구성 목록을 사용해야 한다. 완료된 큐 작업은 원격의 현재 정상 판정을 대신하지 않는다.

## 상태의 의미

| 상태 | 현재 근거와 한계 |
| --- | --- |
| 보관 완료 | 서버가 완료 당시 모든 청크·전체 해시를 검사하고 서명 완료 기록을 게시함 |
| 검토 승인 | 현재 관리자 토큰 요청의 마지막 유효 `good`. `actor` 문자열은 개인 인증이 아님 |
| 시험 통과 | 로컬 보고서의 `trial_passed`. 해당 백업·계획의 고정 DB 검사이며 보고서는 무서명 |
| 현재 자료 확인 | 내려받기에서 실물 바이트를 검사함. 주기적 검사 상태나 가용성 SLA는 아직 없음 |
| 운영 복구 승인 | 일반 경로의 현재 `good` 확인. 승인 전 시험의 `operational_restore_authorized`는 항상 false |

서버 `recommended`는 완료와 마지막 `good`의 조합이다. DB 시험 통과·현재 청크 가용성까지 뜻하지 않는다. 승인 전 시험이 통과해도 `recommended=false`이며 원격 판정은 바뀌지 않는다. 일반 시험 결과도 마지막 조회 이후 취소될 수 있고 전체 서비스 가동·RPO/RTO를 증명하지 않는다. 실행자 서명·인증된 개인별 권한·다중 승인·주기적 실물 검증은 후속이다.

## 장애 범위와 취소

서명이 유효한 제어 객체의 귀속을 확인할 수 있으면 해당 번들의 게시/검토 공백을 개별 보류한다. 목록은 건강한 `items`와 `unavailable`을 함께 반환하며 다음 cursor는 검사한 ID 기준이다. 하나의 번들이 보류되어도 독립적으로 검증되는 다른 번들은 조회할 수 있다. 귀속 불명·카탈로그 유실·전체 구조 오류는 계속 전역 보류한다. 오류를 정상 상태로 해석하거나 임의로 카탈로그를 재생성하지 않는다.

취소는 별도 한정된 논리 예산과 디스크 여유 정책을 사용한다. 일반 업로드가 한도에 도달해도 남은 취소 예산으로 기록할 수 있으며 게시 의도가 영속화된 뒤에는 과거 정상 판정을 추천하지 않는다. 예약 예산 소진·실제 ENOSPC·스토리지 고장을 무조건 해결하지는 못한다. 응답 실패를 취소 성공으로 간주하지 말고 같은 요청 ID/내용으로 재시도한다.

대용량 완료 검사는 공유 저장소 잠금 밖에서 바이트를 읽고, 게시 직전에 구성 목록·파일 신원·판정을 재확인한다. 취소 요청은 별도 제어 요청 슬롯을 사용한다. 커널 I/O 정지나 무한 지연에 대한 실시간 처리 보장은 아니다.

## TLS와 검증 환경

사설 PKI의 신뢰 CA를 `tls_ca_pem`에 설정하면 내장 공개 CA 대신 그 목록만 사용한다. 서버 인증서 이름과 체인 검사는 유지하며 HTTP와 함께 사용할 수 없다. PEM 전체 상한은 64KiB, 인증서는 최대 16개다. 큐 등록 시 PEM 원문 SHA-256을 고정하므로 미완료 큐의 CA 목록을 바꾸어 재전송하지 않는다. TLS CA 목록은 보관 수신증명의 서명키 목록·키 교체 기능과 별개다.

```bash
python3 scripts/bundle-operations-scenarios.py --bin-dir target/release \
  --report /tmp/argos-bundle-operations-new.json
```

`--pg-root /path/to/trusted/postgresql/root`를 추가하면 PostgreSQL 18 native dump의 승인 전 시험·상속 FD 차단을 함께 검사한다.

시험은 새 임시 CA/서버 인증서와 loopback TLS 프록시, 합성 DB를 사용한다. 인증서 신뢰·호스트명 거부, stage 삭제, 게시 직전 작업자 종료, 임대 만료, 원격 완료 뒤 ACK 유실·서버 재시작, 승인 전 시험과 승인/취소를 확인한다. 호스트의 신뢰 저장소나 방화벽을 변경하지 않는다. 전용 SQLite 시험에는 지원하는 Linux x86_64 GNU·일반 사용자·bubblewrap·user namespace·Linux 5.11 이상 close_range 지원가 필요하며 조건이 없으면 무격리 시험으로 대체하지 않는다.

실제 에이전트·보관·복구 서버 3대, 운영 TLS 프록시·인증서 배포, 호스트별 패키지 의존성과 물리 네트워크 장애는 별도의 시험 환경이 필요하다. 이 스크립트의 한 호스트 검증으로 해당 범위를 완료했다고 표시하지 않는다. 실제 실행 결과는 [검증 기록](PLATFORM_VALIDATION.md)을 따른다.
