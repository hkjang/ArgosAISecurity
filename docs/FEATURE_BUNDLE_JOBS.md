# 번들 전체 작업의 영속 등록과 자동 재개

v0.7.0의 `vault bundle enqueue`는 청크뿐 아니라 **구성 목록, 청크 참조, 원격 완료 요청 의도**를 같은 큐에 저장한다. 등록이 성공하면 준비 디렉터리와 원본 파일을 제거해도 `vault queue drain`이 청크 전송부터 원격 완료 증명 저장까지 이어 간다. 기존 [예약 전송 타이머](FEATURE_VAULT_SCHEDULER.md)도 같은 drain 명령으로 처리한다.

```bash
argos vault bundle prepare --file /srv/export/orders.backup.sqlite3 \
  --out /var/lib/argos-upload/prepared-orders \
  --original-path /srv/orders.sqlite3 --plan /srv/export/orders-plan.toml

argos vault --vault-config /etc/argos-upload/vault-upload.toml bundle enqueue \
  --stage /var/lib/argos-upload/prepared-orders \
  --directory /var/lib/argos-upload/queue --max-bytes 268435456

argos vault queue jobs --directory /var/lib/argos-upload/queue
argos vault queue show-bundle --directory /var/lib/argos-upload/queue --id <번들_ID>
argos vault --vault-config /etc/argos-upload/vault-upload.toml queue drain \
  --directory /var/lib/argos-upload/queue --max-items 16
```

`prepare`만 성공한 상태에서는 전송에 필요한 자료가 큐에 없다. **enqueue의 성공 결과를 확인한 뒤에만** 준비 자료의 수명주기를 변경한다. `publish`·직접 `upload`도 계속 제공하지만 영속 작업으로 등록한 번들은 수동 publish를 실행할 필요가 없다.

## 등록 성공의 의미

등록은 원격 통신을 하지 않는다. 구성 목록의 크기·ID·총 바이트·청크 순서를 검사하고 각 청크의 크기·SHA256 및 전체 파일 SHA256을 대조한다. 중복 청크는 하나의 큐 항목을 공유하되 전체 해시는 원래 순서와 반복 횟수대로 계산한다.

1. 큐의 대상과 여유 슬롯을 확인한다. 구성 목록의 같은 번들 ID가 이미 있으면 같은 내용과 유효한 청크 참조에 한해 기존 작업을 반환하고, 다른 내용은 거부한다.
2. 전역 큐 잠금을 잡지 않은 상태에서 고유 청크를 큐 아래 전용 `.bundle-spool-*` 디렉터리에 복사·동기화한다. 파일은 `0600`, 디렉터리는 `0700`이다.
3. 짧은 파일/DB 잠금 구간에서 **모든 신규 청크의 활성 개수·본문 바이트·완료 이력 슬롯**을 한꺼번에 검사한다. 중간에 다른 생산자가 큐를 채웠으면 전체 등록을 거부한다.
4. 고정 청크를 본문 경로로 게시하고 디렉터리를 동기화한 뒤, 청크 항목·번들 구성 목록·참조를 하나의 SQLite FULL 트랜잭션으로 커밋한다. 이 시점 이후에만 성공 결과를 반환한다.

청크 데이터 전체를 메모리에 쌓지 않고 한 번에 최대 16MiB를 읽는다. 준비 중 로컬 임시 스냅샷은 최대 1GiB가 필요할 수 있으며 활성 큐 논리 바이트 한도와 별도의 디스크 여유가 필요하다. 기존 완료 청크는 검증한 수신증명과 ID를 재사용하며 동일 큐의 다른 번들과도 공유할 수 있다. 아직 pending인 청크를 재사용할 때는 같은 번들의 재등록도 포함해 큐 본문의 권한·크기·전체 해시를 잠금 밖에서 검사하고 최종 잠금에서 파일 식별 정보가 그대로인지 확인한다. 검증 도중 완료된 청크는 서명 수신증명으로 대체한다. 큐 본문이 유실·변조됐거나 검증 이후 다른 생산자가 미검증 청크를 등록했다면 성공을 반환하지 않으며 준비 자료를 보존해 원인을 해결한 뒤 재시도해야 한다.

잘못된 청크나 한도 초과로 실패하면 빈 큐 DB·잠금·본문 디렉터리가 초기화됐을 수 있지만 번들 작업을 등록 완료로 보고하지 않는다. 최종 게시 중 I/O 오류나 강제 종료가 발생하면 미참조 본문이 남을 수 있다. 다음 변경 작업은 DB 무결성을 확인한 뒤 게시되지 않은 본문을 정리한다. 구성 목록이나 참조가 손상되었으면 정리·전송을 거부한다.

정상 오류 반환에서는 준비용 spool을 제거한다. 프로세스를 강제 종료하면 `.bundle-spool-*` 흔적이 남을 수 있으며 자동 삭제하지 않는다. 해당 큐의 등록 생산자를 멈추고 현재 등록 작업이 없음을 확인한 다음 운영자가 조사·정리한다. 이것은 성공한 번들 작업이나 전송 재개에 필요한 정식 본문 경로가 아니다.

## 청크와 게시 단계

작업의 `state`는 `pending` 또는 `complete`, `phase`는 다음과 같다.

| phase | 의미 |
|---|---|
| `register` | 청크 완료를 기다리거나, 고정 구성 목록 등록을 재시도하는 단계 |
| `complete` | 구성 목록의 서명 수신증명을 저장했으며 원격 전체 해시 검증·완료 증명을 요청할 단계 |
| `done` | 구성 목록 수신증명과 전체 바이트에 결합한 서버 완료 증명을 로컬에 저장한 상태 |

drain은 고유 청크 **전부의 서명 수신증명**이 archive에 있어야 게시 작업을 선택한다. 게시 가능한 작업을 우선하여 많은 일반 파일 전송 때문에 완료 요청이 계속 밀리지 않게 한다. 한 배치의 `max-items`는 청크 전송과 게시 시도의 합산 예산이다. 구성 목록 등록과 완료 요청은 각각 별도 시도로 계산하며 각 시도에는 HTTP 한 번만 수행한다. 기존 16건 타이머·클라이언트 최대 300초 요청 제한·90분 서비스 제한과 같은 예산을 사용한다.

각 게시 시도는 무작위 임대 토큰·만료·시도 횟수를 먼저 커밋하고 잠금과 DB 연결을 닫은 뒤 HTTP를 호출한다. 임대는 요청 시간 제한에 30초를 더한다. 상태 반영 직전에 동일 임대 토큰과 유효기간을 확인하므로 오래된 작업자가 다른 작업자의 완료 상태를 덮어쓰지 못한다.

등록 응답을 받지 못하면 같은 구성 목록을 다시 등록한다. 완료 응답이 유실되거나 응답 이후 프로세스가 종료돼도 같은 완료 요청을 재시도한다. 서버의 불변 구성 목록과 기존 서명 완료 증명을 확인한 뒤 로컬 작업을 완료한다. 구성 목록·에이전트·서명키·전체 해시가 다른 응답은 성공으로 기록하지 않는다.

**보관 완료는 정상본 승인이나 복구 시험 통과가 아니다.** 로컬 작업의 `recommended`는 항상 `false`다. 원본의 판정 이력 주장을 원격 Good으로 승격하지 않으며, 현재 원격 판정과 실제 복구 준비도는 번들 show/review/test에서 확인한다. 등록과 완료 요청은 원격 관리자 판정을 변경하지 않는다.

## 상태·오류·한도

`queue jobs`는 전체 계수와 최근 최대 100개 작업 요약을, `queue show-bundle --id`는 오래된 작업을 포함한 구성 목록·참조·서명 증명을 조회한다. 모두 읽기 전용이며 통신하거나 큐를 이전하지 않는다. `queue status`의 `bundle_jobs`에도 같은 집계가 있다.

| 필드 | 해석 |
|---|---|
| `total`, `pending`, `complete`, `leased` | 전체 작업·미완료·완료·유효 임대 수 |
| `capacity` | 완료 이력을 포함한 작업 최대 1,000개 |
| `completed_chunks`, `unique_chunks` | 원격 수신증명이 영속화된 청크와 필요한 고유 청크 수 |
| `attempts`, `last_error`, `next_retry_ms` | 게시 시도 횟수·고정 오류 코드·다음 게시 시각 |
| `lease_expires_ms` | 작업자 종료 뒤 임대를 다시 가져갈 수 있는 시각 |
| `earliest_retry_ms` | 미완료 작업의 게시 재시도·임대 만료를 고려한 가장 빠른 시각. 청크 전송 완료도 필요 |
| `items_truncated` | 최근 100개 이외의 작업이 존재함 |

기존 `drain.attempted/sent/failed/remaining_pending`은 청크·일반 객체 집계다. 번들 게시 집계는 `attempted_jobs/completed_jobs/failed_jobs/remaining_jobs`와 `jobs` 배열에 나타난다. 객체 또는 작업 실패가 있으면 CLI는 결과 JSON을 출력한 뒤 비영 종료한다. `attempted + attempted_jobs <= max_items`이며 마지막 청크에서 예산을 다 쓰면 다음 timer 호출이 구성 목록 등록을 이어간다. 모든 청크가 sent라도 `remaining_jobs > 0`이면 번들 완료는 아직 끝나지 않았다.

번들 응답 파싱·서명·프로토콜 결합을 세부 분류할 수 없는 실패는 `bundle_response_or_state_invalid`로 기록한다. 실패의 backoff는 5초부터 최대 1시간이다. 인증·용량·요청 거부·연결/시간 초과·서명 불일치는 고정 오류 코드로 기록하고 토큰·원격 본문은 저장하지 않는다. 시간 기준은 로컬 벽시계이므로 시계 변경이 임대·재시도에 영향을 줄 수 있다. 느린 로컬 저장소와 DB 무결성 검사도 짧은 잠금 경합 오류를 일으킬 수 있다.

기존 활성 큐 한도(기본 1,000개/256MiB, 최대 10,000개/8GiB)와 청크 archive 예약 총합 100,000개는 유지한다. 별도로 번들 작업 전체 1,000개를 보존하며 자동 제거하지 않는다. 각 구성 목록은 최대 256KiB·청크 최대 64개다. 작업 한도에 도달하면 기존 작업·청크를 모두 완료한 뒤 큐와 완료 이력을 보존하고 새 경로로 전환한다. 새 큐는 이전 큐의 중복 판정 이력을 공유하지 않는다. `export-archive`는 **청크 수신증명만** 내보내며 번들 구성 목록·완료 작업의 백업을 대신하지 않는다.

## 형식 이전과 신뢰 경계

schema v1/v2 큐의 상태와 기존 수신증명은 읽기 전용으로 조회할 수 있다. 첫 변경 작업에서 기존 active/archive 이력을 보존하고 번들 작업 테이블을 더해 schema v3로 이전한다. v1 수신증명 이동과 v3 테이블 생성은 같은 트랜잭션이다. 중단되면 SQLite의 journal 복구에 맡기며 형식·테이블·참조 유실을 빈 큐로 재생성하지 않는다. v3 큐는 이전 바이너리로 다시 여는 것을 지원하지 않는다.

큐의 주소·에이전트·서명 키·고정 공개키·loopback 허용 여부에 더해, 자체 CA를 지정했다면 CA PEM 원문의 SHA256도 고정한다. 예전 설정의 CA 없음은 계속 호환한다. CA·대상·키가 달라진 설정은 전송 전에 거부하고 토큰만 교체할 수 있다.

로컬 큐는 현재 UID/root의 삭제·변조를 막는 보안 경계가 아니다. NFS 동기화·전원 차단·실제 업무 DB의 정합성은 별도 검증이 필요하다. 단위 회귀는 stage 삭제 후 단계별 재개, 원격 완료 ACK 유실·만료 임대 교체, 전체 등록 한도·해시·ID 결합, DB 게시 중단의 원자성, 이전 형식 보존, 오류·자격 증명 비노출을 확인한다.
