# 원본 서버 없이 복구하는 원격 번들

복구 번들은 **최대 1 GiB의 백업을 16 MiB 청크로 나누고, 원격 보관 서버의 목록·manifest·검토 이력만으로 새 파일에 재조립**한다. 원본 에이전트 DB나 로컬 백업 인덱스가 없어도 관리자 보관 자격 증명과 고정 공개키로 조회·다운로드할 수 있다. 운영 파일 덮어쓰기·서비스 자동 시작은 수행하지 않는다.

기존 단일 객체 API의 최대 64 MiB 상한은 유지한다. 번들은 하나의 큰 HTTP 업로드가 아니라 작은 객체들과 별도의 완료 단계다. 에이전트가 자동 업로드를 시작하지 않으며 운영자가 명령을 실행한다. [원격 보관 설정](FEATURE_REMOTE_VAULT.md), [서버 용량 보호](FEATURE_VAULT_CAPACITY.md), [전송 대기열](FEATURE_VAULT_QUEUE.md)의 인증·용량·재시도 경계를 함께 적용한다.

## 명령 예

업로드 설정에는 개별 에이전트 토큰을, 조회·검토 설정에는 관리자 토큰을 사용한다. 아래 ID는 실제 명령이 반환한 값으로 대체한다.

```bash
mkdir -m 700 /srv/private-bundles
argos vault bundle prepare --file /srv/offline/orders.backup \
  --out /srv/private-bundles/orders-stage --original-path /srv/orders/orders.sqlite3 \
  --version 42 --plan /srv/offline/orders-plan.toml
argos vault --vault-config /etc/argos/vault-client.toml bundle upload \
  --stage /srv/private-bundles/orders-stage
argos vault --vault-config /etc/argos/vault-admin.toml bundle list --agent-id web-01
argos vault --vault-config /etc/argos/vault-admin.toml bundle show --agent-id web-01 --id BUNDLE_ID
# 내용과 복구 시험을 독립 검토한 뒤 승인
argos vault --vault-config /etc/argos/vault-admin.toml bundle review \
  --agent-id web-01 --id BUNDLE_ID --request-id REVIEW_42 --decision good \
  --actor reviewer --reason "업무 백업과 복구 시험 대조"
argos vault --vault-config /etc/argos/vault-admin.toml bundle fetch \
  --agent-id web-01 --id BUNDLE_ID --out /srv/private-bundles/orders-restored.backup
```

대기열을 통한 전송은 `bundle enqueue --stage STAGE --directory QUEUE --max-bytes 1073741824`, `queue drain --directory QUEUE`, `bundle publish --manifest STAGE/manifest.json` 순서다. 각 단계에 같은 대상의 `--vault-config`를 사용한다. `bundle test --agent-id ID --id BUNDLE_ID --out NEW_DIR`는 현재 정상 판정을 확인하고 새 경로에 받은 백업과 내장 계획으로 DB 복구 시험을 실행한다. 계획 없는 일반 파일은 이 명령의 DB 시험 대상이 아니다.

## 준비와 내용 결합

`bundle::prepare(source, stage, metadata)`는 일반 파일을 한 번 스트리밍해 새 0700 디렉터리에 다음 파일을 만든다. 부모 디렉터리도 현재 계정의 전용 0700 경로여야 한다.

- `chunks/<SHA256>.bin`: 최대 16 MiB의 0600 청크 파일. 같은 내용의 반복 청크는 한 파일을 공유한다.
- `manifest.json`: 모든 청크 준비 후에만 게시하는 0600 manifest.

manifest에는 무작위 `bundle_id`, 형식·준비 시각, 원래 절대 경로·선택적 백업 버전·참고 검토 이력·선택적 복구 계획 TOML, 전체 SHA-256·바이트 수, **순서가 있는** 청크 해시·크기를 담는다. 복구 계획 원문은 최대 64 KiB, manifest 전체는 최대 256 KiB다. 허용 입력은 1바이트~1 GiB, 청크는 최대 64개다. 원본 경로는 자료의 출처 정보이며 복구 대상 경로로 자동 사용하지 않는다.

읽기 전후 inode·크기·수정 시각·ctime과 마지막 경로 신원을 검사하고 symlink·특수 파일을 거부한다. 변경을 감지하면 완성 manifest를 게시하지 않는다. 실패한 준비 디렉터리에 부분 청크가 남을 수 있으므로 별도로 보존·정리하고 새 준비 경로를 사용한다. 준비한 바이트는 원본의 이후 변경과 독립적이다. 이 검사는 애플리케이션 일관성이나 백업의 업무상 정상 판정을 대신하지 않는다.

## 미완료와 완료

전송은 다음 순서로 진행한다.

1. 에이전트 업로드 토큰으로 immutable manifest를 등록한다. 상태는 미완료이며 같은 에이전트·번들 ID에 다른 manifest를 덮어쓸 수 없다.
2. 기존 `backup` 객체 API에 청크를 전송한다. 서버는 동일 해시·종류 재전송을 중복 저장하지 않는다.
3. 완료 요청에서 서버가 모든 청크의 현재 바이트·서명 수신증명·에이전트·종류·크기·해시와 순서대로 계산한 전체 SHA-256을 확인한다.
4. 서버가 서명한 완료 기록을 보관하고 카탈로그 참조를 커밋한 뒤에만 완료를 반환한다.

청크가 없거나 손상되었거나 전체 해시가 다르면 완료로 표시하지 않는다. 직접 전송 API `upload_prepared`는 이 절차를 수행하며 같은 준비 디렉터리로 다시 실행할 수 있다. 준비 디렉터리의 변경된 청크는 전송 전에 거부한다. 이미 완료된 번들도 manifest·청크의 기존 서명과 내용 결합을 사용한다.

대기열을 사용할 때는 각 청크를 `backup` 종류로 먼저 등록하고 `queue drain`으로 전송한다. 기본 대기 바이트 상한은 256 MiB이므로 더 큰 번들은 `--max-bytes`를 명시한다. 전송 후 `register_manifest`와 `complete`를 호출해 최종 게시한다. 청크의 큐 등록·전송·번들 완료는 하나의 트랜잭션이 아니다. 각 큐 항목의 수신증명과 **번들의 완료 상태**를 모두 확인해야 한다. 서버 완료 검사는 manifest만 있으면 가능하므로 청크 전송 뒤 준비 청크를 잃어도 manifest로 게시를 마칠 수 있다.

## 원격 관리자 검토와 취소

업로드한 manifest의 `review_history`나 “정상본” 주장은 참고 자료다. **원격 현재 판정은 최초 `unknown`**이다. 완료된 번들에 대해 관리자 토큰으로 `good` 또는 `revoked` 검토를 추가한다. 각 요청에는 재시도용 고유 `request_id`, 담당자 `actor`, 검토 근거 `reason`이 필요하다. 같은 요청 ID와 같은 내용의 재시도는 이력을 늘리지 않으며 다른 내용으로 재사용하면 거부한다.

서버는 검토마다 에이전트·번들 ID·manifest·완료 기록·직전 검토 해시·순번·요청 내용을 결합해 서명한다. 판정 취소도 새로운 서명 기록이며 기존 manifest·청크·완료·검토 객체를 삭제하지 않는다. 마지막 유효 검토가 `good`인 완료 번들만 `recommended=true`다. `unknown`, `revoked`, 미완료, 서명/이력 검증 실패를 추천하지 않는다. 다시 승인하려면 새 요청 ID로 새 검토를 추가한다.

에이전트 업로드 토큰은 관리자 조회·검토 권한을 갖지 않는다. 관리자 토큰이 검토 권한의 인증 수단이며 `actor` 문자열은 별도 개인 신원 인증이 아니다. 등록과 완료는 에이전트 토큰에 결합한 호스트 범위로만 처리한다. 목록·상세·청크 다운로드와 검토는 관리자 토큰을 요구한다.

**취소 요청도 용량 검사 대상이다.** quota나 저장 실패로 HTTP 507/오류가 발생하면 취소가 적용되었다고 판단하면 안 된다. 취소 게시 의도가 영속 저장된 뒤 오류가 나면 과거 `good`를 추천하지 않도록 해당 번들의 조회·복구를 보류한다. 이는 취소 완료 표시가 아니므로 용량·저장 문제를 해결한 뒤 같은 요청 ID·내용으로 재시도해야 한다. 실패를 성공으로 표시하거나 과거 기록을 덮어써 공간을 확보하지 않는다.

## 조회와 새 파일 복구

관리자 목록은 에이전트 ID로 범위를 고정하고 번들 ID 오름차순 cursor를 사용한다. HTTP API 기본 20개, CLI 기본 100개, 허용 1~100개이며 `next_cursor`로 다음 페이지를 조회한다. 미완료 번들도 완료 여부와 현재 판정을 구분해 표시한다. 목록 요약은 HTTPS로 받은 서버 상태이며 개별 서명 패키지가 아니다. 상세 조회는 manifest 수신증명, 서명 완료 기록, 모든 검토 이력과 파생 상태를 반환한다.

`fetch`의 기본 조건은 현재 `good`인 완료 번들이다. 각 청크의 수신증명과 같은 다운로드 바이트를 검증하고 순서대로 임시 파일에 쓴다. 전체 크기·해시를 확인한 뒤 현재 상태를 다시 조회하여 전송 중 취소나 카탈로그 공백이 생기면 최종 파일 게시를 보류한다. 성공한 결과만 전용 0700 부모의 **새 0600 경로**에 원자적으로 게시하며 기존 파일·symlink를 덮어쓰지 않는다. 실패한 임시 파일은 정리한다.

명시적 `evidence_only` 선택은 완료된 `unknown`/`revoked` 번들을 조사 자료로 내려받을 때만 사용한다. 정상 복구 승인으로 바꾸는 옵션이 아니며 서명·내용·완료 검사를 생략하지 않는다. 복구 계획은 백업과 함께 보존된 자료이므로 관리자가 검토하고 새 다운로드 경로에 맞춰야 한다. [DB 복구 시험](FEATURE_SERVICE_RECOVERY.md)을 통해 복원 결과를 추가 확인한다.

## 저장·용량·중단 경계

manifest·완료·검토 제어 기록도 기존 서버 객체 계층에 저장하고 전체·에이전트별 바이트와 객체 quota를 소비한다. 서버 내부 종류 `bundle-manifest`, `bundle-completion`, `bundle-review`는 일반 객체 업로드 API에서 거부한다. 청크는 기존 `backup` 종류다. 다른 종류로 같은 해시를 이미 저장한 경우 기존 객체 충돌 규칙을 유지한다.

`.argos-bundles.sqlite3`는 객체 해시 참조와 작은 게시 의도를 기록하는 SQLite FULL 카탈로그이며 `.argos-bundles.ready`와 함께 보관해야 한다. 서버 전체 최대 10,000개·에이전트별 최대 1,000개 번들, 번들별 최대 100개 검토 이력을 허용한다. 마지막 검토 슬롯은 `revoked`만 허용해 정상 판정 상태에서 취소할 공간이 영구 소진되지 않게 한다. 100번째 취소 뒤 재승인은 새 번들에 새 검토로 진행한다. 카탈로그·journal·디렉터리·서명 메타데이터의 물리 할당량은 논리 본문 quota에 그대로 대응하지 않으므로 별도 디스크 여유를 유지한다.

객체와 SQLite는 하나의 파일시스템 트랜잭션이 아니다. 완료/검토는 게시할 동일 서명 바이트를 SQLite 의도로 먼저 보존하고, 객체·수신증명을 게시한 후 카탈로그 참조와 의도 제거를 함께 커밋한다. ACK 유실이나 카탈로그 커밋 실패 뒤에는 같은 단계를 다시 요청한다. 검토의 중단된 요청이 남았다면 새 요청으로 우회하지 않고 같은 ID·내용을 재시도한다. 불완전 객체 게시 자체는 기존 보관 서버와 같이 쓰기를 중단하고 저장소 점검·재시작을 요구할 수 있다.

서버는 시작 시 서명된 번들 제어 객체를 계수하고 카탈로그 참조 수와 대조한다. 표식/DB의 일부가 없거나, 둘 다 없어도 제어 객체가 남아 있거나, 최신 검토 참조가 유실되면 빈 카탈로그로 자동 재생성하지 않는다. 불일치 동안 목록·상세·복구를 보류해 오래된 `good`를 현재 상태로 반환하지 않는다. 다른 번들의 미커밋 제어 객체 때문에 전체 번들 조회가 보류될 수도 있다. 원인 단계의 동일 요청을 재시도하거나 보존한 저장소를 관리자가 점검해야 한다.

원본 서버 없이 복구하는 기능이 **보관 서버까지 유실되어도 복구한다는 뜻은 아니다.** 서버 저장소·카탈로그·서명키의 별도 운영 보존이 필요하다. 동일 UID/root의 디스크·카탈로그 동시 변조, 관리자 토큰 탈취, 서명키 유실·회전, 커널/스토리지 장애, 실제 원격 TLS 배포는 이 로컬 시험만으로 보호하지 않는다. v0.5 이하 서버는 번들 제어 종류와 카탈로그를 지원하지 않으므로 번들을 게시한 저장소를 그대로 이전 버전으로 되돌리지 않는다. 수신/완료 서명은 저장 당시 검증 근거이며 현재 모든 청크의 가용성이나 데이터의 업무상 정상성을 보장하지 않는다. 복구 시 바이트를 다시 검사한다.

## 검증

```bash
cargo test -p argos-vault bundle --locked
```

숫자 loopback HTTP와 임시 합성 데이터로 다음을 확인한다: 원본/준비 디렉터리를 제거한 뒤 원격 전용 복구, 정상 판정·취소·같은 요청 재시도, 청크 누락·변조·전체 해시 불일치, 불변 manifest, 역할 분리, cursor 목록, 제어 객체 quota, 최신 취소/카탈로그 유실 시 보류, SQLite 카탈로그 게시 실패 후 같은 서명 객체 재시도, 16 MiB 반복 청크의 순서·중복 보존. 파일 내용·원본 DB 자격 증명은 운영 시스템에서 가져오지 않는다.
