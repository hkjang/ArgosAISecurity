# 원격 보관 업로드 대기열

전송할 바이트를 로컬에 먼저 보존하고 통신 실패·프로세스 중단 후 같은 대상으로 다시 보낸다. v0.5.0부터 **활성 큐와 완료 수신증명 보관소를 분리**하며 네트워크 대기 중에도 새 항목을 등록할 수 있다. `enqueue`는 통신하지 않고 `drain`만 제한된 배치를 전송한다. 자동 반복은 별도로 설정한 예약 실행을 사용한다. 원격 설정은 [원격 보관](FEATURE_REMOTE_VAULT.md)을 참고한다.

```bash
argos vault --vault-config ./vault-client.toml queue enqueue \
  --directory /var/lib/argos/upload-queue \
  --file ./evidence.json --kind evidence

argos vault queue status --directory /var/lib/argos/upload-queue
argos vault --vault-config ./vault-client.toml queue drain \
  --directory /var/lib/argos/upload-queue --max-items 10

argos vault queue show --directory /var/lib/argos/upload-queue \
  --id <enqueue가_반환한_32자리_hex_ID>
```

큐 경로는 상위 디렉터리가 이미 있고 `..`를 포함하지 않는 절대 경로다. 큐·본문 디렉터리는 현재 계정 소유 `0700`, DB·잠금·본문 파일은 `0600` 단일 링크 일반 파일이어야 한다. 상위 경로의 symlink·다른 계정 쓰기 권한을 거부하며 root 소유 sticky 임시 디렉터리는 허용한다. 토큰은 큐에 저장하지 않고 전송 시 별도 설정에서 읽는다.

## 등록·완료·중복 판정

원본을 한 번 읽으며 크기·변경 여부를 검사하고 동일 바이트의 스냅샷과 SHA256을 저장한다. 등록 이후 원본 변경은 전송 내용에 영향을 주지 않는다. 파일 바이트의 안정성 검사이며 애플리케이션 일관성이나 정상본 판정을 자동 보장하지 않는다.

큐의 주소·에이전트 ID·서명 키 ID·고정 공개키·HTTP loopback 허용 여부는 첫 등록 시 고정된다. 자체 CA를 설정했다면 PEM 원문의 `tls_ca_sha256`도 고정하며, 기존 큐의 CA 없음은 호환한다. 대상·키·CA를 바꾸려면 새 큐를 사용한다. 토큰 교체는 허용한다. 활성 항목과 완료 보관소 양쪽에서 같은 `kind`·SHA256을 조회하여 기존 ID를 반환한다. pending 항목 재등록은 기존 스냅샷의 권한·크기·전체 해시를 다시 확인하며, 유실·변조된 본문을 자동 수리하거나 등록 성공으로 보고하지 않는다. 실패하면 원본을 보존하고 큐를 점검한다. 완료 항목 재등록은 새 전송이나 보관 기간 갱신이 아니다.

전송 직전에 스냅샷 크기·SHA256을 대조하고 확인한 바이트를 보낸다. 수신증명의 서명·키·에이전트·종류·해시·크기를 검증한 다음 같은 SQLite 트랜잭션으로 완료 보관소에 넣고 활성 항목을 제거한다. **완료 커밋 후에만 본문을 삭제한다.** 저장된 수신증명은 해당 업로드의 수신 근거이며 현재 원격 가용성이나 만료 후 존속의 보증은 아니다.

`enqueue-backup`·`enqueue-evidence`는 등록 시 정상본·증거 패키지를 확인한다. 등록 이후 정상본 승인 취소나 정책 변경을 자동 반영하지 않는다. 여러 증거 객체는 독립 전송이므로 반환된 **모든 항목**의 완료와 수신증명을 확인해야 한다. 분할 업로드·사건별 원자적 보관 묶음은 v0.5.0 범위에 포함하지 않는다.

## 네트워크와 분리한 항목 임대

항목을 선택할 때 무작위 임대 토큰·만료 시각·시도 횟수·재시도 시각을 영속화한 뒤 DB와 프로세스 잠금을 닫고 HTTP를 호출한다. 임대 시간은 클라이언트 `timeout_secs`에 30초를 더한 값이다. HTTP 시간 제한은 설정의 1~300초다. 다른 작업자는 임대 중인 항목을 건너뛰며 `enqueue`는 네트워크 응답을 기다리지 않는다.

완료·실패 기록은 임대 토큰이 같고 아직 만료되지 않았을 때만 반영한다. 프로세스 중단 뒤 남은 임대는 만료 후 다시 가져갈 수 있다. 만료되거나 교체된 작업자의 늦은 응답은 새 작업자의 상태와 본문을 바꾸지 못하며 `lease_expired_or_replaced`로 보고한다. 서버 저장 후 ACK가 유실되어도 같은 대상·종류·바이트를 다시 전송하고 서버의 내용 주소 중복 처리를 사용한다.

파일·DB 상태 변경 구간은 프로세스 배타 잠금으로 직렬화한다. 짧은 경합은 최대 2초 기다린 뒤 오류로 끝난다. 대용량 로컬 스냅샷 기록·이력 증가에 따른 DB 무결성/상태 검사·SQLite 복구·최초 스키마 이전도 시간이 필요하므로 모든 상황에서 등록이 즉시 성공한다는 보장은 아니다. 네트워크 대기 전체를 잠그던 v0.4.0의 동작을 제거한 것이다.

`drain`은 1~100회 시도하며 CLI 기본값은 16, 라이브러리 기본값은 10이다. JSON의 `attempted`, `sent`, `failed`, `remaining_pending`은 일반 객체·청크 집계다. 번들 게시의 `attempted_jobs`, `completed_jobs`, `failed_jobs`, `remaining_jobs`도 함께 확인하며 `attempted + attempted_jobs`가 배치 예산을 넘지 않는다. 객체 또는 작업 실패가 있으면 CLI는 JSON을 출력한 뒤 비정상 종료한다. `attempted=0`은 번들 단계만 처리했거나 재시도 대기·다른 작업자의 임대 때문에 발생할 수 있고 완료를 뜻하지 않는다. `status.leased_items`는 아직 만료되지 않은 객체 임대 수, `earliest_retry_ms`는 객체의 재시도 대기와 임대 만료를 함께 반영한 가장 빠른 예정 시각이다. 번들 작업의 임대·예정 시각은 `status.bundle_jobs`를 확인한다.

## 오류와 재시도

실패 대기는 5초부터 두 배씩 증가하여 최대 1시간이다. `attempts`, `next_retry_ms`, `last_error`를 확인한다. 시간은 로컬 벽시계 기준이므로 시계 변경 시 임대와 재시도 일정도 영향을 받는다. 자격 증명·원격 응답 본문을 DB나 오류 메시지에 복사하지 않는다.

| 코드 | 뜻·운영 조치 |
|---|---|
| `interrupted_or_unconfirmed` | 임대 시작 후 아직 결과를 확정하지 못함. 임대 만료·다음 예약 확인 |
| `authentication` | 인증 거부. 서버 권한·클라이언트 토큰 확인 |
| `capacity` | 서버 용량 거부. 보관 서버 사용량·한도·여유 공간 확인 |
| `rate_limit` | 요청 제한. 예약 간격·작업자 수 확인 |
| `server_transient` | 서버 일시 오류. 이후 재시도 |
| `request_rejected` | 그 밖의 요청 거부. 서버 설정·요청 계약 확인 |
| `transport`, `connect`, `timeout` | 전송·연결·시간 제한 오류. 경로와 서버 상태 확인 |
| `response_integrity` | 응답 형식·서명·수신증명 일치 검사 실패. 서버 키·보관 결과 확인 |
| `client_settings` | 클라이언트 설정 오류 |
| `queue_local` | 로컬 스냅샷 경로·크기·해시·읽기 오류. 원본과 큐 보존 후 점검 |
| `lease_expired_or_replaced` | 현재 작업자가 임대 소유권을 잃어 결과 반영을 거부함 |
| `unknown` | 분류할 수 없는 클라이언트 오류 |

오류 분류가 자동으로 인증을 바꾸거나 데이터를 삭제하지 않는다. 기존 v0.4.0 기록의 `snapshot_upload_or_receipt_validation_failed`는 읽을 수 있으며 다음 시도부터 새 분류를 기록한다.

## 용량과 완료 이력 보존

| 제한 | 기본값 | 범위·집계 대상 |
|---|---:|---|
| `enqueue --max-items` | 1,000 | 1~10,000. 임대 중인 항목을 포함한 **활성 항목만** |
| `enqueue --max-bytes` | 256MiB | 1바이트~8GiB. 활성 본문 논리 크기 |
| 완료 보관소와 활성 예약 합계 | 100,000건 | 고정 상한. 완료 예정 항목의 보관 슬롯도 등록 시 확보 |
| 단일 객체 | 클라이언트 설정 | 원격 API 최대 64MiB 이하 |
| `status.items` | 최근 100건 | 활성·완료 모두 포함, 누락은 `items_truncated` 표시 |
| 이력 내보내기 | 최대 100,000건 | 파일 256MiB, 행 8KiB 상한 |

완료할 때 활성 슬롯과 본문 예산을 반환하므로 성공 이력이 쌓여도 기본 1,000개 활성 상한을 소모하지 않는다. `items_total`은 활성·완료 합계이고 `pending_items`가 활성 사용량이다. `archive_items`, `archive_capacity`, `archive_slots_available`로 별도 이력 보관 용량을 확인한다. 100,000건에 도달하면 **새 등록만** 거부하며 이미 등록한 항목은 확보한 슬롯을 사용해 끝까지 완료할 수 있다.

논리 바이트 한도는 SQLite·journal·수신증명·파일시스템 할당량을 포함하지 않는다. 완료 이력의 건수 상한은 물리 디스크 quota가 아니며 별도 여유 공간과 운영 백업이 필요하다. 큐는 암호화 저장소가 아니다.

## 이력 내보내기·검증·새 큐로 전환

```bash
# 현재 계정 소유 0700 보관 디렉터리의 새 파일로만 게시한다.
argos vault queue export-archive \
  --directory /var/lib/argos/upload-queue \
  --out /var/lib/argos/receipt-exports/archive-20260927.jsonl

argos vault queue verify-archive \
  --file /var/lib/argos/receipt-exports/archive-20260927.jsonl \
  --pubkey <고정_Ed25519_공개키_hex>
```

내보내기는 시작 시 완료된 항목의 상한을 고정하고 100건씩 짧게 읽어 스트리밍한다. 이후 완료된 항목은 다음 내보내기에 포함된다. 각 서명을 검증하며 header·완료 기록·개수/해시 trailer가 모두 작성된 임시 파일을 동기화한 뒤 새 `0600` 파일로 독점 게시한다. 기존 출력은 덮어쓰지 않고 DB 이력을 삭제하지 않는다. 정상 종료 전 중단되어 남은 `.argos-vault-archive-*.tmp`는 최종 출력이 아니다.

`verify-archive`는 입력을 읽기 전용으로 열어 고정 공개키에 대한 개별 수신증명, 항목 일치, 중복, 개수·내용 해시·trailer·파일 변경 여부를 검사한다. 잘린 파일·잘못된 키·중복 기록은 거부한다. **파일 인덱스와 내보내기 시각 자체는 서명되지 않는다.** `archive_authenticated=false`이며 개별 수신증명 검증을 파일 전체의 출처나 모든 과거 이력이 빠짐없이 포함됐다는 인증으로 해석하면 안 된다.

상한에 가까워지면 등록 생산자를 중지하고 남은 항목을 전송하여 `pending_items=0`, `leased_items=0`인지 확인한다. 완료 이력을 새 파일로 내보내고 검증한 뒤 기존 전용 큐 디렉터리도 운영 보존한다. 생산자·예약 실행을 새로운 큐 경로로 바꿔 계속 운영한다. 자동 삭제·자동 전환·기존 이력 가져오기는 제공하지 않는다. **중복 판정은 한 큐 안에서 유지되며 새 큐로 전환하면 이전 큐의 중복 판정은 이어지지 않는다.** 기존 원격 객체의 동일 바이트 재전송은 서버의 내용 주소 중복 처리에 따른다.

## v0.4.0에서 이전·중단 복구

새 큐는 없거나 완전히 빈 디렉터리에만 초기화한다. DB·잠금·본문 디렉터리 일부만 남거나 형식·스키마·대상·서명 기록이 불완전하면 기존 파일을 보존하고 오류로 중단한다. 유실된 DB를 빈 큐로 재생성하지 않는다.

기존 schema v1은 `status`·`show`·내보내기에서 읽기 전용으로 조회할 수 있다. 첫 `enqueue`·`drain`에서 완료 수신증명을 전부 검증한 뒤 하나의 SQLite 트랜잭션으로 schema v3로 이전한다. schema v2도 첫 변경 작업에서 v3로 이전한다. 완료 이력은 archive 테이블로 이동하고 활성 항목·ID·재시도 상태·스냅샷은 보존한다. 이전 중에는 해당 큐 작업을 잠시 멈추고 미리 전용 디렉터리를 백업하는 운영 절차를 권한다. v3로 이전한 큐를 v0.6.0 이하 바이너리로 다시 여는 것은 지원하지 않는다.

스냅샷과 SQLite는 하나의 트랜잭션이 아니다. 본문 파일·디렉터리를 먼저 동기화하고 SQLite `synchronous=FULL`로 항목을 게시한다. 게시 전 중단된 미참조 본문과 완료 커밋 후 남은 본문은 다음 변경 작업이 DB 무결성·스키마·대상 기록을 확인한 뒤 정리한다. 완료 본문은 저장된 수신증명도 재검증한다. SQLite journal은 직접 지우지 않고 SQLite의 복구에 맡긴다. 읽기 전용 명령은 큐를 정리하거나 이전하지 않는다.

로컬 파일시스템의 `flock`·SQLite 동기화 의미를 전제로 한다. NFS 등 원격 파일시스템, 커널·스토리지 장애에서의 영속성, 동일 UID/root의 변조·삭제 방지를 보장하지 않는다. 회귀 시험은 1,001개 실제 loopback 전송의 활성 슬롯 재사용·오래된 이력 중복 판정, 전송 중 다른 프로세스의 등록, 작업자 종료·임대 재확보·늦은 ACK 거부, v1 이전·손상 시 보존, 내보내기 검증·잘림 거부를 포함한다.

## 번들의 자동 게시

v0.7.0의 `bundle enqueue`는 구성 목록·고유 청크·게시 작업을 함께 등록한다. `queue drain`과 예약 전송이 청크 및 register/complete 단계를 같은 요청 예산 안에서 재개한다. `queue jobs`·`show-bundle`과 `status.bundle_jobs`로 작업을 조회한다. 완료 이력 내보내기는 청크 수신증명에 해당하며 번들 작업 DB를 대신하지 않으므로 큐 교체 시 `bundle_jobs.pending=0`, `bundle_jobs.leased=0`도 확인하고 큐 전체를 보존한다. [작업 한도와 복구](FEATURE_BUNDLE_JOBS.md)를 따른다.
