# 원격 보관 업로드 대기열

전송할 파일을 먼저 로컬에 보존하고, 통신 실패나 CLI 중단 후 같은 대상으로 이어 보낸다. `enqueue`는 네트워크를 사용하지 않으며 **명시적으로 실행한 `drain`만** 전송한다. 에이전트가 자동 업로드를 시작하는 기능은 아니다. 원격 서버·키·토큰 설정은 [원격 보관](FEATURE_REMOTE_VAULT.md)을 참고한다.

```bash
argos vault --vault-config ./vault-client.toml queue enqueue \
  --directory /var/lib/argos/upload-queue \
  --file ./evidence.json --kind evidence

argos vault queue status --directory /var/lib/argos/upload-queue
argos vault --vault-config ./vault-client.toml queue drain \
  --directory /var/lib/argos/upload-queue --max-items 10

argos vault queue show --directory /var/lib/argos/upload-queue \
  --id <enqueue가_반환한_32자리_hex_ID>
```

큐 경로는 상위 디렉터리가 이미 있고 `..`를 포함하지 않는 절대 경로를 지정한다. 상대 경로는 디렉터리를 생성하기 전에 거부한다. 처음 등록할 때 큐와 본문 디렉터리를 `0700`, SQLite DB·잠금·본문 파일을 `0600`으로 만든다. 현재 계정 소유여야 하며 상위 경로의 symlink·다른 계정 쓰기 권한을 거부한다. root 소유 sticky 임시 디렉터리는 허용한다. 토큰은 큐에 저장하지 않고 각 `drain` 호출의 별도 설정에서 읽는다.

## 저장과 전송 규칙

- 원본 파일을 한 번 읽으면서 크기·변경 여부를 검사하고, 그 바이트의 스냅샷과 SHA256을 저장한다. 등록 후 원본이 바뀌어도 보낼 내용은 바뀌지 않는다. 일반 파일의 바이트 스냅샷이며 애플리케이션 일관성이나 정상본 판정을 자동으로 보장하지 않는다.
- 큐 하나의 주소·에이전트 ID·서명 키 ID·고정 공개키·HTTP loopback 허용 여부를 처음 등록 때 고정한다. 이후 다른 대상 설정으로 등록하거나 전송하면 거부한다. 다른 서버나 키를 쓰려면 새 큐를 사용한다. 토큰 교체는 같은 대상의 자격 증명 교체로 허용한다.
- 같은 큐에서 `kind`와 SHA256이 같은 파일을 다시 등록하면 기존 ID를 반환한다. 이미 완료된 항목도 중복 등록하지 않는다. 보관 기간을 갱신하는 기능은 아니다.
- 전송 직전에 스냅샷을 한 번 읽어 저장한 크기·SHA256과 대조하고, 확인한 동일 바이트를 HTTP 본문으로 사용한다. 잘못된 수신증명 서명·키 ID·에이전트·종류·해시·크기는 완료 처리하지 않는다.
- 검증된 수신증명을 SQLite에 먼저 커밋한 뒤 로컬 본문을 지운다. 상태가 `sent`인 항목에는 저장된 서명 수신증명이 남는다. 이는 해당 업로드의 수신 근거이며 원격 보관의 현재 가용성·만료 후 존속까지 보장하지 않는다.

`enqueue-backup`·`enqueue-evidence`를 쓰면 CLI가 정상본·증거 패키지를 등록 시점에 확인한다. 이후 정상본 승인이 취소되거나 원본 정책이 바뀌어도 등록한 바이트를 자동 취소·재판정하지 않는다. 증거 패키지의 여러 객체는 하나의 원자적 원격 전송이 아니므로 반환된 **모든 항목**의 `sent`와 수신증명을 확인해야 한다.

## 재시작과 오류

새 큐는 존재하지 않거나 완전히 빈 전용 디렉터리에만 초기화한다. 잠금·본문 디렉터리·DB 중 일부만 남아 있거나 DB 형식·스키마·대상 기록이 불완전하면 오류로 중단하고 기존 파일을 보존한다. DB가 유실된 경로를 빈 큐로 다시 만드는 기능은 없다. 초기화 중단 흔적은 별도로 보존·점검한 뒤 새 경로를 사용한다.

스키마와 대상 기록을 하나의 SQLite `synchronous=FULL` 트랜잭션으로 초기화한다. 스냅샷의 파일/디렉터리를 동기화한 뒤 같은 동기화 수준의 트랜잭션으로 항목을 게시한다. 파일과 SQLite를 함께 묶는 단일 트랜잭션은 아니다. 게시 도중 중단되어 남은 미참조 스냅샷, 완료 커밋 뒤 아직 지우지 못한 본문은 다음 `enqueue` 또는 `drain`에서 기존 DB의 무결성·스키마·대상 기록을 확인한 뒤에만 정리한다. SQLite journal은 직접 지우지 않고 SQLite의 복구에 맡긴다. `status`·`show`는 파일 생성·정리·통신을 하지 않는다.

각 전송 전에 시도 횟수와 재시도 시각을 커밋한다. 서버가 저장했지만 ACK가 유실되면 항목은 `pending`으로 남고, 다음 호출에서 같은 대상·종류·바이트로 재전송한다. 원격 서버의 내용 주소 기반 중복 처리를 사용한다. 자동 반복 루프는 없다.

실패의 대기 시간은 5초부터 두 배씩 증가하고 최대 1시간이다. `attempts`, `next_retry_ms`, `last_error`를 확인한다. 오류는 토큰이나 원격 응답 본문을 반사하지 않는 고정 코드로 기록한다. 프로세스 중단 직후에는 `interrupted_or_unconfirmed`, 스냅샷/전송/수신증명 검사 실패에는 `snapshot_upload_or_receipt_validation_failed`가 남는다. 시간 기준은 로컬 벽시계이므로 시계 변경 시 재시도 시점도 영향을 받는다.

`drain`은 한 번에 1~100개만 처리하며 CLI 기본값은 16개다. 라이브러리 `DrainOptions::default()`는 10개다. JSON의 `attempted`, `sent`, `failed`, `remaining_pending`을 확인한다. 실패 항목이 있으면 CLI는 결과 출력 후 비정상 종료한다. 재시도 시각 전이라 `attempted=0`일 수 있으며, 이는 전송 완료를 의미하지 않는다. 각 HTTP 요청에는 클라이언트 설정의 시간 제한이 적용된다.

## 용량과 장기 운영

| 제한 | 기본값 | 허용 범위·집계 대상 |
|---|---:|---|
| `enqueue --max-items` | 1,000 | 1~10,000개. `pending`과 `sent` 이력을 모두 포함 |
| `enqueue --max-bytes` | 256MiB | 1바이트~8GiB. `pending` 본문 크기의 합계 |
| 파일 한 개 | 클라이언트 설정 | 원격 API의 최대 64MiB 이하 |
| 상태 상세 목록 | 최근 100개 | 전체 집계는 모두 계산하고 목록 누락은 `items_truncated` 표시 |

기록 상한은 완료 이력까지 세며 이력을 자동 삭제하지 않는다. 더 높은 상한으로 새 항목을 등록할 수 있지만 최대 10,000개는 유지한다. 상한에 도달한 큐는 `remaining_pending=0`인지 확인하고 실행 중인 작업을 종료한 뒤, 서명 수신증명을 포함한 전용 디렉터리를 운영 보존하고 다른 경로에 새 큐를 시작한다. 완료 본문은 이미 정리되지만 DB 수신증명은 보존 대상이다. 최근 100건 밖의 기록은 `queue show --id`로 조회한다. 출력의 `receipt` 객체를 별도 JSON 파일에 저장하면 기존 수신증명 검증 도구로 독립 검증할 수 있다.

바이트 상한은 본문 논리 크기 기준이다. SQLite·journal·수신증명·임시 파일 및 파일시스템 할당 단위까지 포함한 디스크 할당량은 아니므로 별도 여유 공간이 필요하다. 큐는 암호화 저장소가 아니다.

## 잠금·검증 범위

한 큐의 `enqueue`·`drain`은 프로세스 간 배타 잠금을 사용한다. 동시에 실행하면 두 번째 작업은 busy 오류로 끝나며, 잠금은 프로세스 종료 시 운영체제가 해제한다. 전송 동안에도 잠금을 유지한다. `status`·`show`는 SQLite의 읽기 전용 조회를 사용한다.

로컬 파일시스템의 `flock`·SQLite 동기화 의미를 전제로 한다. NFS 등 원격 파일시스템, 커널·스토리지 장애에서의 영속성, 동일 UID/root의 변조·삭제를 검증한 기능은 아니다. 이 경우 별도 운영 검증과 백업이 필요하다.

회귀 시험은 원본 변경 뒤 동일 바이트 전송, ACK 유실·재시작 재전송, 재시도 대기, 위조 수신증명 거부, 대상 변경 거부, 용량 상한·중복 등록, 중단 후 고아 파일 정리, DB 유실·빈 DB·불완전 스키마·초기화 중단 시 파일 보존, 읽기 전용 상태 조회와 프로세스 잠금을 확인한다. 모의 HTTP는 숫자 loopback 주소만 사용하며 외부 보관 서비스에 연결하지 않는다.
